Contract 002: Rename a person and enforce unique names

Amendment 1 Items 1-6 are documentation corrections with no behaviour change. Item 7 (Amendment 1b) records behaviour added during the review round, which is non-breaking. You re-approve all of it together. api-dev reported defects after running the merged implementation. I checked each against the code in exercise1/api and its tests, and probed the .NET 10.0.13 runtime where the code alone could not settle it.

  1. Route-value binding messages (data.md "Program.cs"; openapi.yaml ValidationFailed).
    • Revision 1 set only the three property accessors. That still let /Person/99999999999 echo the value (The value '99999999999' is not valid.), because action parameters use the non-property variants.
    • The contract now also requires SetNonPropertyAttemptedValueIsInvalidAccessor(_ => "The value is not valid.") and SetNonPropertyValueMustBeANumberAccessor(() => "The value must be a number."). The implementation already has both (Program.cs:17-18).
    • Resulting bodies:
      • PUT /Person/abc (also 1.5, 99999999999, notanumber) returns errors: {"personId":["The value is not valid."]}.
      • 0 and -1 return the [Range] message The field personId must be between 1 and 2147483647.
    • tests.md P8 adds notanumber and 1.5.
  2. 415 body (openapi.yaml, types.ts, tests.md P9).
    • Revision 1 said the 415 body is ProblemDetails. It actually depends on the request:
      • A non-JSON Content-Type such as text/plain is rejected by endpoint routing, and the 415 has an empty body.
      • A missing Content-Type header gives a 415 with a ProblemDetails body.
    • Clients must key on the 415 status only. The UI already treats 415 as a propagated HttpErrorResponse, so nothing changes for it.
  3. JSON property order (cosmetic). The body is written as person, success, message, responseCode. Order is not significant, and the examples are reordered to match.
  4. Invisible set made reviewable (data.md).
    • The literal invisible characters are replaced by the implementation's \uXXXX escapes and a table of 28 code points, with names and categories.
    • openapi.yaml's NamePattern describes the same set and states the count.
  5. U+180E: the report was wrong, and the actual behaviour is now documented.
    • The report said string.Trim() removes a leading or trailing U+180E. It does not. On .NET 10.0.13, char.IsWhiteSpace((char)0x180E) is false (category Cf since Unicode 6.3), and a probe confirmed that "Ada" + (char)0x180E keeps its length (4) after Normalize.
    • So U+180E is rejected anywhere in a name, edges included, with a 400. It is never silently dropped, and it is not in the trim set.
    • data.md now defines the trim set exactly: the 25 char.IsWhiteSpace code points. Since 1b, the API and the migration use the same set.
    • tests.md R13 asks for the two edge cases. They are still missing from the merged tests (see "Open" below).
  6. Read-back after update finds no row: 404 (data.md step 5, openapi.yaml 404).
    • If the person is deleted between the save and the read-back, the handler returns the same 404 envelope as for an unknown id. A 200 with person: null is never returned.
    • Now tested by H17.
  7. NON-breaking needs re-approval Amendment 1b: behaviour added during the review round (commits 72bb7b2 and fab7b22, merged as 55ae823).
    • The migration trims and guards on the same whitespace set as the API.
      • AddUniquePersonNameIndex.TrimCharacterCodes lists the 25 char.IsWhiteSpace code points, not only space, tab, LF and CR.
      • The guard now also aborts, with a clear message and no data change, when any name is empty once trimmed.
      • The abort message changed. It now contains "or are empty once trimmed", and the listing hint is SELECT Id, Name FROM Person ORDER BY lower(trim(Name));.
      • Tests M9-M13.
    • Raw length bound. A name longer than InputRules.MaxRawLength = 800 characters as sent is rejected before normalisation, by [ValidName] (400, key Name) and in the handler. Tests R23, H18 and P16.
    • Request body limit.
      • [RequestSizeLimit(4096)] on PUT /Person/{personId}: on Kestrel, a larger body gets 413, and the body of that response is unspecified. Every valid name fits.
      • The in-memory TestServer does not enforce the limit, so P17 accepts 413 or 400. The 413 is a QA check on real Kestrel.
      • 413 does not appear in the generated Swagger.
    • Concurrent delete between load and save. DbUpdateConcurrencyException maps to the same 404 "Person not found" as the empty read-back. Test H16.
    • Validation order. The 400 checks run before the 404 lookup:
      • PUT /Person/999999 with an invalid name gives 400, not 404 (P18a).
      • PUT /Person/0 with a valid name gives 400 with key personId, from [Range] (P18b).
    • Also documented, unchanged from main: supplementary-plane letters (surrogate pairs) are rejected (R22). P7 checks that body-shape 400s do not echo submitted tokens.

Open (test gap, no code change): the merged tests do not yet cover the R13 U+180E edge cases. U+180E before or after a name gives 400 (verified by probe), but only an inner U+180E is tested.

Changes you are approving

alters data Migration trims existing names. It removes whitespace at either end, using the same 25 Unicode whitespace characters that the API trims (Amendment 1b). It runs only after a guard has proven two things: trimming creates no collision, and no name becomes empty. If either fails, the migration aborts with a clear message and changes nothing. See plan Q1.

behaviour change POST /Person (code not edited): a duplicate that differs only in case, or is identical, is now rejected by the database. The existing controller catch returns 500 {success:false, message:"An error occurred while saving the entity changes. See the inner exception for details.", responseCode:500}. It used to be 200 and created a duplicate. Padded names ("Ada ") still insert. Task 006 fixes both. See plan Q2.

non-breaking for ASCII Shared name rule tightened (also applies to GET /Person filters and GET /Person/{name}). These now return 400:

  • invisible letters and marks: 28 code points, U+034F, U+115F, U+1160, U+17B4, U+17B5, U+180B-U+180F, U+3164, U+FE00-U+FE0F, U+FFA0 (named in data.md)
  • a combining mark that does not follow a letter
  • more than 3 marks in a row

Reads now NFC-normalise their input, so an NFD query finds an NFC name. The 400 shape and message are unchanged.

There are no breaking changes to existing response shapes.

New endpoint: PUT /Person/{personId}

The body is { "name": "..." }, at most 4096 bytes. The JSON content type is required. Property order in responses is not significant. Validation (400) always runs before the lookup (404) and the uniqueness check (409).

The name rule (defined once, reused by task 006): reject more than 800 characters as sent. Otherwise NFC-normalise the name and trim it (Unicode whitespace), then require 1 to 100 characters, made of letters (each followed by at most 3 combining marks), ASCII digits, space, period, apostrophe and hyphen, with no invisible code points. The name is stored in that normalised form.

Rename to own name or a different casing of it succeeds. Rank, duty title and duties are never touched. There is no Location header.

Database

  • Person.Name becomes TEXT COLLATE NOCASE NOT NULL, with unique index IX_Person_Name, added by the new migration AddUniquePersonNameIndex. Existing migrations are untouched.
  • Case folding is ASCII-only (SQLite), so Émile and émile are distinct. This is the accepted decision from task 001.
  • Stored names written before this task are not NFC-normalised. The migration trims the same whitespace set as the API.
  • Down drops the index and the collation. Trimmed names stay trimmed.

UI client

StargateApi.updatePerson(personId: number, name: string): Observable<UpdatePersonOutcome>

  • It sends PUT /api/Person/{personId} with body {name}.
  • It emits {status:'updated', person}, {status:'notFound'} (404), {status:'conflict'} (409) or {status:'invalid', errors} (400).
  • Other errors propagate, including 413 and 415.

The new types in models.ts are UpdatePersonRequest, UpdatePersonResult and UpdatePersonOutcome. Amendment 1 does not change them. There is no screen.

Not decided by this contract

  • The body of a 413.
