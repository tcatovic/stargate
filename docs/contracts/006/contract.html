Contract 006: ASCII-only names, exact name filter, validated POST /Person

Revision 3: what changed from revision 2 (the review round changed the merged code; this revision makes the contract match it)

  1. Name rule: at least one ASCII letter or digit. Punctuation-only names (., .., ', -, . -) are now 400 on all four endpoints. Why: .. breaks the UI's URL building (/api/Person/.. resolves to /api/), and none of them is a name. New pattern ^(?=[ .'-]*[A-Za-z0-9])[A-Za-z0-9 .'-]+\z and new message text (below). Files: openapi.yaml (NameRule, NameFilter, ValidationFailed), data.md, tests.md, this page, the plan.
  2. Malformed JSON gets generic messages only. AllowInputFormatterExceptionMessages = false in Program.cs. A body such as [], {"name":4242}, a bare string or truncated JSON is still 400, but the messages are fixed framework text (for example {"$":["The input was not valid."],"request":["The request field is required."]}), never .NET type names, paths, line numbers or byte positions. Why: the parser messages leaked internal type names. Files: openapi.yaml (ValidationFailed), data.md (new section), tests.md (M1).
  3. The 400 message set for name is now exact (it was already the code's behaviour): rule failure gives the rule message; missing or null gives "The Name field is required."; blank gives both, in that order. File: openapi.yaml.
  4. Tests (tests.md): weak tests removed (R13, R21, R25's source-text checks, F5, create H3, update P13, duplicate rows); no-echo checks strengthened (ProblemAssert); new C6, C7, P18, P19, R27, R28, F6, F7, P20 and M1. Why: tests.md must match the merged suite.
  5. Open issues recorded (not part of this task, not fixed): SQL built by string interpolation in CreateAstronautDuty, and no authentication on any write endpoint. See "Open" below.
  6. No UI type changes; types.ts is untouched.

  • New: ASCII-only name rule, for all four endpoints that use it. The NFC step, the invisible-character set, the combining-mark limit and the 800-character raw bound are removed. Breaking changes (all accepted by the user):

  • Punctuation-only names (rev. 3), such as ., .., ' and -, get 400 on the same four endpoints. They were accepted before (on GET filters and PUT, and stored by POST).
  • Non-ASCII names get 400 on GET /Person (filters), GET /Person/{name}, PUT /Person/{personId} and POST /Person. This includes previously valid names such as Émile, NFD input, and a no-break space at an edge. The validation message wording changes.
  • GET /Person?name= is now exact (case-insensitive, trimmed). A partial name returns an empty list. For example, ?name=elena no longer finds Elena Vasquez.
  • POST /Person changes in several ways:
    • Body: { "name": "..." } instead of a bare string (400 or 415).
    • Success: 201 (was 200), with a Location header.
    • Duplicate: 409 (was 500 or a duplicate row).
    • Invalid name: 400 (was stored).
    • New statuses: 415 and 413.
    • 500: empty body (it used to contain the exception message).

The name rule (one definition, used everywhere)

trim ASCII whitespace (tab, LF, VT, FF, CR, space)   -- nothing else is trimmed
then 1..100 characters, each one of:  A-Z a-z 0-9 space . ' -
with at least one ASCII letter or digit                (rev. 3)
pattern ^(?=[ .'-]*[A-Za-z0-9])[A-Za-z0-9 .'-]+\z
        (no IgnoreCase, no \d, no Unicode normalisation; the lookahead is linear)

Message (exact text, display only): "Use only English letters (A-Z), digits, spaces, hyphens, apostrophes and periods, with at least one letter or digit (at most 100 characters)."

  • Uniqueness and lookups compare ignoring ASCII case (SQLite NOCASE). For ASCII names that is complete case-insensitivity.
  • GET filters and the GET route check the value as sent, so an edge tab or newline is 400 there. That is unchanged from today, and task 008 can unify it.
  • Seed names, ranks and titles are all valid.

Open: not part of this task, not fixed (recorded in revision 3; the user has not yet decided whether the fix goes into this PR or a separate security task)

  1. Second-order SQL injection through POST /AstronautDuty. Business/Commands/CreateAstronautDuty.cs:56 builds SELECT * FROM [Person] WHERE '{request.Name}' = Name by string interpolation (lines 70 and 100 interpolate person.Id the same way). The registered pre-processor first requires a person whose name equals request.Name exactly (EF, parameterised), so the attacker stores the payload as a name first. Names may contain apostrophes and spaces, and POST /Person has no authentication, so a stored name such as a' OR Id IS 3 OR 'a passes the name rule; POST /AstronautDuty with that name then reads person 3 and writes a duty, detail and rank to person 3. This predates task 006 (before it, POST /Person stored any string); 006 narrows the payload alphabet but does not close it. Fix (deferred): parameterise the queries at CreateAstronautDuty.cs:56, :70 and :100.
  2. The same pattern in GetAstronautDutiesByName.cs:28 (and :38). Today it is not reachable over HTTP, because AstronautDutyController.GetAstronautDutiesByName sends GetPersonByName instead; it becomes exploitable as soon as it is wired up.
  3. No authentication on any write endpoint (POST /Person, PUT /Person/{personId}, POST /AstronautDuty). UseAuthorization is called but no scheme or policy is configured. Unchanged by this task.
