Contract 006: POST /Person becomes a validated create endpoint

One endpoint changes. There is no schema change. The UI gains one client method. The api and ui developers build against this page and the files listed at the bottom, in parallel.

Breaking changes (accepted in the task Decisions, except the Location target, which is Question 1 below):

  • Request body: { "name": "..." } replaces the bare JSON string "...". A bare string now gets 400 (with application/json) or 415 (any other content type).
  • Success: 201 Created (was 200), responseCode: 201, plus a new Location header.
  • Duplicate: 409. It used to be a 500 carrying EF's message, or a 200 with a second row for padded or NFD names.
  • Invalid name: 400 (was 200 and stored). There are also new 415 and 413 responses.
  • 500 body: empty in Production. It used to carry the exception message.
  • id is now nullable: always a number on 201, null on 409.

Request

POST /Person
Content-Type: application/json        (charset allowed; body at most 4096 bytes)

{ "name": "Ada Lovelace" }            (unknown properties ignored)

Validation uses the shared rule from 002, unchanged. The name is checked against an 800-character bound as sent, then NFC-normalised and trimmed, and then must be 1 to 100 characters of letters (each followed by at most 3 combining marks), digits, space, ., ' and -, with none of the 28 invisible code points.

Responses

StatusWhenBody

400The body is empty, not an object (including a bare string), or malformed; name is missing, null or not a string; or it fails the name ruleValidationProblemDetails, never echoing the input
409The name is taken, ignoring ASCII case and surrounding whitespace, after NFC. This covers both the pre-check and a concurrent create rejected by the unique index{ "id": null, "success": false, "message": "A person with this name already exists", "responseCode": 409 }, no Location
413Body over 4096 bytes (on Kestrel)Unspecified; key on the status
415The Content-Type is not JSON (empty body), or there is no Content-Type at all (ProblemDetails)Key on the status
500An unexpected faultEmpty in Production; the developer page in Development only

Checks run in this order: 415 and 413 first, then 400, then 409. A successful create of a name that is then posted again returns 409; the endpoint is not idempotent.

Location header differs from the task decision

  • Value: /Person?name= followed by the stored name, encoded with Uri.EscapeDataString (relative and ASCII-only). Example: Zoë O'Brien gives /Person?name=Zo%C3%AB%20O%27Brien.
  • Why not /Person/{name}: task 008 removes that route, after which the header would point at a 404. GET /Person?name= works today (contains match) and after 008 (exact match).
  • Why the encoding is required: a probe showed that Kestrel answers 500 for a non-ASCII header, after the row is already stored.
  • The UI does not read Location.

UI client

createPerson(name: string): Observable<CreatePersonOutcome>
  // POST /api/Person { name }  (name unmodified)
  // 201 with id >= 1        -> { status: 'created', id }
  // 201 with a bad id       -> error 'Malformed create response'
  // 409                     -> { status: 'conflict' }
  // 400                     -> { status: 'invalid', errors }
  // anything else           -> HttpErrorResponse propagates

New types in models.ts: CreatePersonRequest { name: string }, CreatePersonResult extends BaseResponse { id: number | null }, CreatePersonOutcome.

Domain rules

  • Rule 1: names are normalised (NFC and trim), then the handler runs a NOCASE pre-check. The existing unique index IX_Person_Name is the guarantee, and a lost race maps to 409. Parallel creates of the same name give exactly one 201.
  • Rule 2: only a Person row is inserted. AstronautDetail and AstronautDuty are untouched, and tests compare dumps of both. The new person lists with "" rank and title and null dates.

Removed

  • CreatePersonPreProcessor (never registered, so dead code). The duplicate check now lives only in the handler, as for PUT.
  • The POST action's try/catch, which returned ex.Message.

Open questions (answer when approving)

  1. Location target. Recommended: /Person?name=, as this contract is written. The alternative is to keep /Person/{name} and make task 008 rewrite it.
  2. Compatibility characters and look-alikes (Ａｄａ, ﬁ, Cyrillic а) remain distinct, valid names; this rule is not changed here. Recommended: accept for 006, and decide on a separate hardening task (a comparison key column with NFKC and full case folding) versus accepting the limit.
  3. 500 body. It is empty rather than a "generic message". Recommended: accept, and add a global ProblemDetails exception handler as its own task.
