Contract 007: AstronautDuty endpoints

Amendment 1: what changed, and why. After implementation, the developer and reviewers found places where the contract text did not match the merged code. I checked each one against the code and tests. The amendment documents the merged behaviour. No status code, response shape or field changes, so there is no new breaking change and nothing new for the UI.

  1. Whitespace-only ?name= (spaces, %09, %0A): 400 with only ["The name field is required."], not [required, NameRule]. MVC binds a whitespace-only query value to null. The status was always right; the message list was wrong. Files: openapi.yaml (ValidationFailed), data.md section 4, tests.md G7, plus new G7b.
  2. Repeated ?name=a&name=b: the first value is used. One person (or 404) results and the values are never merged. This is now documented and pinned by tests.md G7c. Files: openapi.yaml (GET), data.md section 2, tests.md.
  3. Which person a name resolves to: now an exact-case match first, then the lowest id (was: lowest id). All three lookups (POST, GET ?name=, GET /Person/{name}) agree. This is observable only on a database that predates the unique-name index. Files: openapi.yaml, data.md sections 1a, 2 and 3, tests.md section 5a.
  4. tests.md matches the merged suite. 20 IDs were added and A15, A16, K2, G6 and G8 were corrected. The mutation map is fixed: dropping the explicit COLLATE NOCASE changes nothing on a migrated database, because the column itself is NOCASE there. Only H8 and CH17 (pre-index schema) catch it.
  5. Known gaps recorded (data.md section 6). Date offsets: the earlier text was imprecise, and the brief for this amendment was partly wrong. A numeric offset, including +00:00, is converted to server-local time. Z is not, which I verified with a probe. Also recorded: no transaction or open-duty index; the rules 3-7 defects; and a deployment follow-up to refuse to start outside Development with pending migrations.

Unchanged: types.ts (UI types), every status code, every body shape, the breaking-change list below.

Files: openapi.yaml · data.md · types.ts · tests.md. No schema change, no migration, no new package.

Security (first). Names, ranks and titles never alter SQL: they are passed only as parameters (EF LINQ for the create, static Dapper SQL for the read). Each request resolves the person once, by a trimmed, exact, case-insensitive name match. If several stored names match, which can only happen on a pre-index database, the exact-case match wins, then the lowest id. Only that person's id is used afterwards. CreateAstronautDutyPreProcessor is deleted. The task 006 demonstration (a' OR Id IS 3 OR 'a rewriting Tomas Lindqvist's duties) must now write only to the person whose name it is. That is tested over HTTP, with every other person's rows byte-identical before and after.

GET /AstronautDuty?name=

  • 200: {person: PersonAstronaut, astronautDuties: AstronautDutyItem[], success:true, message:"Successful", responseCode:200}. Duties are ordered by start date, newest first, then by id descending. A person without an assignment gets [].
  • 400: ValidationProblemDetails under key name. A missing, empty or whitespace-only name gives only "The name field is required." (Amendment 1). Over 100 characters, a disallowed character, or no letter or digit gives the name-rule message. The input is never echoed.
  • A repeated name uses the first value (Amendment 1). Send it once.
  • 404: unknown name (fixed body above). 500: empty body in Production.

POST /AstronautDuty

  • Body: {name, rank, dutyTitle, dutyStartDate}, all required. Unknown properties are ignored.
  • Order of checks: 415 and 413, then 400, then 404, then 409. Nothing is written on any error.
  • 409 messages (fixed): "A duty with this title and start date already exists for this person", or "The person's duties were changed by another request" (a concurrent first duty lost the race on the existing unique index for the person's detail).
  • On success, the duty-history behaviour (rules 3-7) is unchanged for the same valid input. Rank and title are now trimmed, and when two duties tie on the latest start date, the one with the higher id is the one closed.

Known, deliberately out of scope (task 009)

  • A first RETIRED duty sets CareerEndDate to the start date instead of start minus 1.
  • RETIRED is case-sensitive.
  • Back-dated and same-day duties are accepted, and an already-closed latest duty is closed again. A later duty does not clear CareerEndDate.
  • There is no transaction around read, decide and write, and no unique index for the open duty or for person plus start date. Two concurrent POSTs for a person who already has a duty can both succeed and leave two open duties. There are no concurrency tests.
  • Date offsets: a dutyStartDate with a numeric UTC offset (for example -05:00, and also +00:00) is converted to the server's local time before .Date. The stored date can therefore move by a day, depending on the server's time zone. The 1900-2100 bounds still hold. A value ending in Z, or a plain YYYY-MM-DD, keeps its written date.
