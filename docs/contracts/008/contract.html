Breaking changes

BREAKING GET /Person/{name} is removed. A GET on /Person/{x} now gets 405 Method Not Allowed with header Allow: PUT and an empty body. That path belongs to PUT /Person/{personId}, so routing answers "method not allowed", not 404. No handler runs and no person data is returned. Use GET /Person?name=<name>. An unknown person is 200 with people: [] (it was 404). A HEAD on the same path was already 405 before this task. Only its Allow value changes, from GET, PUT to PUT.

Accepted at approval (plan Q1): 405 rather than the task's original 404, with no route constraint added to PUT.

BREAKING (UI internal) StargateApi.getPerson and GetPersonByNameResult are removed. No component used them.

Not breaking

  • GET /Person parameters and response shapes are unchanged. The parameters are name, rank and dutyTitle, all optional, case-insensitive exact, combined with AND. The 200 response is { people[], success, message, responseCode }, with "" rank and title for unassigned people. The 400 response is ValidationProblemDetails keyed name/rank/dutyTitle, and the input is never echoed.
  • Trimming matches the writes. Surrounding ASCII whitespace (tab, LF, VT, FF, CR, space) is removed before validation. A leading or trailing control character, or padding beyond 100 characters, now returns 200 instead of 400. No input that was accepted before is now rejected.
  • Over-long values return 400 with exactly one message, the shared name-rule message (it was "The field x must be a string with a maximum length of 100.").
  • Binding (unchanged, now written down): parameter names are case-insensitive, a repeated parameter uses its first value, and unknown parameters are ignored. query, query.name, query.*, query[0] and indexed name[0] are not aliases and never switch a filter or its validation off.
  • Swagger: /Person keeps maxLength and pattern and loses only minLength: 0. GET /AstronautDuty's name gains maxLength and pattern. /Person/{name} and GetPersonByNameResult are gone.
  • PUT /Person/{personId} is unchanged: PUT /Person/abc is 400 with a JSON body and 415 with no body, the same as before.

Known, deliberately accepted (Amendment 1)

  • A value made only of non-ASCII whitespace means "no filter". ?name=%C2%A0 (NBSP) or ?rank=%E3%80%80 binds to null, because MVC uses Unicode-aware IsNullOrWhiteSpace. The response is 200 with everyone (test Q6k). This contradicts the InputRules summary comment (InputRules.cs:10), which says non-ASCII whitespace is always invalid. That holds only when the value has other characters too (%C2%A0Elena%20Vasquez is 400, Q6j). It is documented and tested as intended: the result is the same public list as GET /Person, nothing extra is exposed, and BASE behaved the same way.
  • The Q8 hostile-value loop accepts either 200 (empty list) or 400 for each row, by design. It asserts "never a 500, never wider results, never a write", not which side of the name rule each string falls on. The exact 400s are pinned in Q7, and the 4000-character value has its own test asserting 400.

Domain rules

  • Rule 1: one exact, trimmed, case-insensitive lookup by name (GET /Person?name=), backed by the unique NOCASE index. On a database that predates the index and still holds case variants, the list shows every variant.
  • Rule 2: SQL is unchanged. Unassigned people are matched by name alone and never by rank or dutyTitle.

Security note

When the object is bound with a plain [FromQuery] GetPeople query, ?query=x&name=%25 returns 200 with every person: validation and filters are skipped (observed in planning). The contract requires Name = "" on the action parameter. Tests Q5a-Q5k lock that in, across every prefix-like shape listed in amendment item 4. Mutation M1 (dropping Name = "") turns them red.
