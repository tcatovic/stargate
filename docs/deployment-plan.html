Stargate ACTS: Deployment Plan

GitHub, Docker Compose locally, Azure Container Apps and Azure SQL in production. Status: planning only, nothing built yet.

Goal. Push the monorepo to GitHub, run the whole system locally with one docker compose up, and deploy it to Azure as a public test project that anyone can browse.

Decisions made

TopicDecision
HostingAzure Container Apps for both api and web (scale to zero)
DatabaseAzure SQL Database, free offer. Local dev uses SQL Server in Docker
Public accessRead-only for anonymous visitors. Write endpoints require an API key
ImagesGitHub Container Registry (GHCR), free
Azure login from CIOIDC federated credential, no stored Azure secrets
InfrastructureBicep in infra/
Local runOne docker-compose.yml: db, api, web

Architecture

Local

docker compose up
  db    SQL Server 2022   (named volume, health check)
  api   .NET 10 API       (waits for db, applies migrations, seeds dev data)
  web   nginx             (serves the Angular build, proxies /api to api)

browser -> http://localhost:8080 -> web -> /api -> api -> db

Production

GitHub (main)
  |  Actions: build, test, push images to GHCR, deploy via OIDC
  v
Azure resource group
  Container Apps environment
    web  (public ingress, nginx, proxies /api to api)
    api  (internal ingress only, reached through web)
  Azure SQL Database (free offer)
  Log Analytics workspace (Container Apps logs)

The api app has internal ingress only. Browsers reach it through the web app's /api proxy, so there is one public origin and no CORS configuration. Swagger stays off in production.

Constraints and risks

Blockers before anything is public.

  • SQL injection. Several handlers build SQL from request values. Fix and test before any public deployment.
  • Provider switch. Production uses SQL Server, so the EF provider changes from SQLite and the initial migration is regenerated. Existing migration files are not edited; the old one is replaced as part of the switch because there is no production data yet.
  • Free Azure SQL limit. The free offer has a monthly compute allowance. Configure it to auto-pause until next month rather than bill, so the demo can go offline late in the month but never costs money. The UI must show a clear "database unavailable" state.
  • Cold starts. Both apps scale to zero, so the first request after idle takes a few seconds and the database may need to wake. The smoke test must tolerate this with retries.
  • Cost guard. Create an Azure budget alert at a low amount before provisioning anything.
  • Read-only public. Anonymous requests may only use GET endpoints. POST endpoints require the X-Api-Key header, checked in middleware and compared in constant time. The key lives in Container Apps secrets, never in the repo or the UI bundle.
  • Sandbox limits. This sandbox blocks the .NET and NuGet download hosts, and Azure logins need your machine. Steps marked you are run by you; I supply the exact commands.

Phases

Phase 1: Foundation code you

  • Allow the .NET hosts in the sandbox, then verify dotnet build -warnaserror on .NET 10 and fix any package breaks.
  • Create the GitHub repo, set the git user, make the baseline commit, push.
  • Add .github/workflows/ci.yml: API build and test, format check, UI npm ci, test and build, CodeQL, Dependabot for NuGet, npm and Actions.
  • Branch protection on main: CI must pass, pull requests required.

Done when: a pull request runs CI green on GitHub.

Phase 2: Harden the API code

  • Remove interpolated SQL (EF LINQ or parameterised Dapper), with hostile-input tests.
  • Fix the duties endpoint calling the wrong query, and the null dereferences.
  • Validation pipeline returning 400, 404 and 409 with ProblemDetails; global exception handler.
  • Duty rules 3-7 in one transaction, with unit tests.
  • API-key middleware on write endpoints; anonymous GET allowed; rate limiting on all routes.
  • /health (liveness) and /health/ready (database).
  • Create exercise1/api.Tests and a root .sln.

Done when: hostile input is rejected, a write without a key returns 401, and coverage is above the CI gate.

Phase 3: Containers and SQL Server code

  • Switch to Microsoft.EntityFrameworkCore.SqlServer; regenerate the initial migration; add a unique index on Person.Name.
  • Dev-only seeder with sample people and duties. Replaces the commented SeedData.
  • exercise1/api/Dockerfile: multi-stage, non-root, health check.
  • exercise1/ui/Dockerfile and nginx.conf: Angular build, then nginx with SPA fallback and the /api proxy.
  • Root docker-compose.yml and .dockerignore files.
  • Migrations are applied by a one-shot step, not by app start-up in production.

Done when: docker compose up from a clean clone shows seeded people at http://localhost:8080.

Phase 4: Azure and deployment code you

  • you Create the budget alert, the resource group, and the GitHub OIDC app registration (commands provided).
  • Bicep: SQL server and free-offer database, Log Analytics, Container Apps environment, api (internal) and web (external) apps, secrets for the connection string and API key.
  • .github/workflows/deploy.yml on merge to main:
    1. build and test
    2. build and push api and web images to GHCR, tagged with the commit SHA
    3. build an EF migration bundle and apply it to Azure SQL
    4. update the two Container Apps to the new image tags
    5. smoke test /health/ready and GET /Person through the public URL, with retries for cold starts
  • GitHub production environment with a manual approval gate.
  • Separate manually-triggered infra.yml to apply Bicep.

Done when: merging to main and approving the gate deploys a working site.

Phase 5: Go live code you

  • Deploy to the generated Container Apps URL and run the smoke tests.
  • UI shows a clear message when the free database is paused or unreachable.
  • Repo README.md with the live link, run, test and deploy instructions, and the architecture sketch.
  • Optional later: custom domain, a nightly job that re-seeds demo data, and a minimum of one web replica to avoid cold starts.
