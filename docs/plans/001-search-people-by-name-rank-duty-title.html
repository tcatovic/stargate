1. Summary and verdict

GET /Person gains optional name (case-insensitive contains), rank and dutyTitle (case-insensitive exact) query filters combined with AND, implemented as one static, parameterised Dapper query over the existing LEFT JOIN. GET /Person/{name} becomes a parameterised, case-insensitive exact lookup that returns 404 for an unknown name. All four inputs are bounded (100 characters) and restricted to the shared character set (letters, digits, space, hyphen, apostrophe, period) using ASP.NET Core model validation, which returns a 400 ValidationProblemDetails. The two touched actions lose their try/catch, so they no longer return ex.Message. The UI client gains listPeople(filters?), and getPerson maps 404 to null.

Verdict: multi

The work spans two platforms (api, ui) with a real contract between them: query parameter names and encoding, the 404 and 400 semantics and bodies, and the unchanged response shape. Once the contract is fixed, the UI client and its Vitest tests do not depend on the API code, so api-dev and ui-dev can work in parallel. The UI part is small, but it is a separate platform with its own toolchain and tests, and a contract avoids drift on the 404 and 400 bodies. No db or infra work is needed (no schema change).

3. Approach and decisions

D1. Query design (GetPeople)

I keep Dapper (the repo's read pattern) and use one static SQL string with named parameters. Values are never concatenated, and the SQL text does not vary with the input.

SELECT a.Id AS PersonId, a.Name, b.CurrentRank, b.CurrentDutyTitle, b.CareerStartDate, b.CareerEndDate
FROM [Person] a
LEFT JOIN [AstronautDetail] b ON b.PersonId = a.Id
WHERE (@NamePattern IS NULL OR a.Name LIKE @NamePattern ESCAPE '\')
  AND (@Rank IS NULL OR b.CurrentRank = @Rank COLLATE NOCASE)
  AND (@DutyTitle IS NULL OR b.CurrentDutyTitle = @DutyTitle COLLATE NOCASE)
  • Normalisation in the handler: each filter is trimmed. A null, empty or whitespace-only value becomes null (no filter). Model binding already turns ?name= and ?name=%20%20 into null (verified).
  • LIKE escaping: NamePattern = "%" + EscapeLike(name) + "%", where EscapeLike replaces \ with \\ first, then % with \% and _ with \_. The SQL uses ESCAPE '\'. In C#, write the SQL as a verbatim or raw string so the backslash reaches SQLite unchanged. Validation already rejects %, _ and \ over HTTP, so escaping is defence in depth for direct MediatR callers and handler tests.
  • Rule 2: for an unassigned person, b.CurrentRank and b.CurrentDutyTitle are NULL, so NULL = @x is not true and the person is excluded by any rank or dutyTitle filter. A name-only filter still includes them.
  • No ORDER BY change (Decision: no sorting). Order stays unspecified, as today. Tests compare sets.
  • Pass the CancellationToken through CommandDefinition.

D1b. Single-person lookup (GetPersonByName)

SELECT a.Id AS PersonId, a.Name, b.CurrentRank, b.CurrentDutyTitle, b.CareerStartDate, b.CareerEndDate
FROM [Person] a
LEFT JOIN [AstronautDetail] b ON b.PersonId = a.Id
WHERE a.Name = @Name COLLATE NOCASE
ORDER BY CASE WHEN a.Name = @Name THEN 0 ELSE 1 END, a.Id
LIMIT 1
  • The name is trimmed. The match is exact and case-insensitive. LIKE is not used, so % and _ have no wildcard meaning.
  • Until task 002 adds the case-insensitive unique index, case-variant duplicates can exist. The ORDER BY makes the choice deterministic: an exact-case match wins, then the lowest Id.
  • Not found: Person = null, Success = false, Message = "Person not found", ResponseCode = 404. This copies the existing pattern in CreateAstronautDutyHandler from task 005. The message never echoes the input. breaking, as agreed in the task.

D1c. Case-insensitivity in SQLite (verified)

SQLite's LIKE and COLLATE NOCASE fold ASCII letters only. I checked this against SQLite 3.46:

  • LIKE '%ÉLENA%' matches Élena, because É is the same character and the ASCII part folds.
  • LIKE '%élena%' does not match Élena.
  • = 'ÉLENA' COLLATE NOCASE does not match élena.

So a non-ASCII letter matches only in the same case. I recommend accepting this and documenting it. Every seeded value is ASCII, and task 002's case-insensitive unique index on Person.Name will use the same NOCASE semantics, so lookup and uniqueness agree. Full Unicode folding would need ICU, a custom SQLite function, or in-memory filtering, and is not worth it here (see Q3). A characterisation test pins the behaviour so any change is deliberate.

D2. Validation

  • Where: ASP.NET Core model validation on the action parameters. [ApiController] already returns 400 automatically. Each parameter gets [StringLength(100)] and [RegularExpression(InputRules.AllowedCharactersPattern, ErrorMessage = InputRules.AllowedCharactersMessage)]. The route parameter also gets MinimumLength = 1.
  • Shared rule: a new exercise1/api/Business/Validation/InputRules.cs defines MaxLength = 100, AllowedCharactersPattern = @"^[\p{L}\p{M}0-9 .'-]+$" and the message. "Letters" means Unicode letters plus combining marks. "Digits" means ASCII 0-9. The typographic apostrophe (U+2019) is not allowed. Tasks 002 and 006 should reuse this class rather than define the rule again. The pattern is linear, so there is no ReDoS risk.
  • Same rule for rank and dutyTitle: the Decision allows any bounded string with no allowed-values list. The AC still asks for allowed characters, so they use the same character set. Every seeded rank (CPT, MAJ, 2LT, LTC) and title (Pilot, Mission Specialist, Flight Engineer, Commander, RETIRED) passes.
  • Seed data passes: all six seeded names are plain ASCII letters and spaces. A test iterates DevelopmentSeedData.People() and asserts every name, rank and title matches the pattern.
  • 400 body: the framework's ValidationProblemDetails (type, title, status: 400, errors{param: [messages]}, traceId). Error keys are the parameter names (name, rank, dutyTitle). Messages never contain the submitted value (verified). This is already the app's 400 shape for binding errors, and CLAUDE.md names ProblemDetails as the error shape. It is not a BaseResponse. Its status equals the HTTP status.
  • Handlers do not validate. They normalise (trim) and escape only, so direct MediatR callers stay safe even without the 400.

Alternative rejected: a MediatR validation pipeline behaviour returning a BaseResponse 400. CLAUDE.md prefers pipeline behaviours for cross-cutting validation, so I considered this first. I rejected it here for four reasons:

  1. It needs a new generic behaviour, a validator abstraction and DI registrations, which is more code than three attributes.
  2. It would also validate GET /AstronautDuty/{name}, because that endpoint sends the same GetPersonByName request. That changes an out-of-scope endpoint.
  3. Throwing from a behaviour would land in the remaining try/catch blocks as a 500 with ex.Message, because there is no global handler yet.
  4. Swagger would not show the bounds. The framework filter is still cross-cutting (declarative, not copy-pasted), and Swashbuckle emits maxLength and pattern from the same attributes (verified).

D2b. The 500 leak in the touched actions

I remove the try/catch from GetPeople and GetPersonByName in PersonController. An unexpected fault then propagates to the host:

  • Kestrel logs it at Error level and returns 500 with an empty body in Production.
  • Development shows the developer exception page, which is Development only.

This is the smallest change that stops the leak and matches the standard ("controllers free of try/catch"). It also gives better observability than today, where the catch swallows the exception without logging it. CreatePerson and AstronautDutyController are not touched. The global exception handler stays out of scope.

Alternative rejected: keeping the try/catch with a generic message. It keeps a pattern the standards forbid, and it still swallows the exception without a log entry.

D3. Swagger

No XML comments. GenerateDocumentationFile plus TreatWarningsAsErrors would fail the build on CS1591 for every undocumented public member, and NoWarn is not allowed. Instead, use attributes that Swashbuckle 10.3.0 reads (verified in a scratch app):

  • [EndpointSummary] and [EndpointDescription] on the action.
  • [System.ComponentModel.Description] on each parameter.
  • [ProducesResponseType(typeof(GetPeopleResult), 200)], (typeof(ValidationProblemDetails), 400), (typeof(GetPersonByNameResult), 404) and (StatusCodes.Status500InternalServerError) with no type.
  • maxLength, minLength and pattern come from the validation attributes.

D4. UI client

  • listPeople(filters?: PersonFilters): Observable<GetPeopleResult> builds HttpParams. It trims each value and sets only keys whose trimmed value is non-empty, so no filters produce exactly /api/Person. The default HttpUrlEncodingCodec is safe here: it encodes & # + % and space, and leaves only @ : $ , ; = ? / raw, which is legal in a query value (verified in the installed Angular source). No custom codec is needed.
  • getPeople() stays, because app.ts uses it. It delegates to listPeople() and requests the same URL, so app.spec.ts passes unchanged.
  • getPerson(name): Observable<PersonAstronaut | null>. signature change, but there are no callers. It trims the name. A blank name emits null without a request, because /api/Person/ would otherwise hit the list endpoint. It encodes with encodeURIComponent. A 200 emits result.person. A 404 emits null and completes. Any other error (400, 500, network) errors with the HttpErrorResponse.
  • models.ts gains PersonFilters and ValidationProblemDetails. Existing types are unchanged. getDuties is unchanged (out of scope).
  • No new screen and no change to app.ts or app.html.

D5. Test strategy and the new package question

The tests are handler-level, with the existing TestDatabase (a per-test SQLite file migrated to latest) for every filter case, plus controller-level tests that build PersonController with a real IMediator from a ServiceCollection over a per-test database. These prove status codes 200 and 404, that responseCode equals the status, and that exceptions propagate rather than leaking. They do not exercise the MVC pipeline: model validation (400), route decoding and Swagger.

Those need WebApplicationFactory from Microsoft.AspNetCore.Mvc.Testing, which is a new test-only dependency, so CLAUDE.md requires asking first (Q2). I recommend adding it; CLAUDE.md already names this as the integration-test approach. If you decline, two things cover the gap. Rule tests run the same attributes through Validator.TryValidateValue, and QA verifies 400, URL encoding and Swagger with curl against the running app. tests.md marks those cases as tier H so either path is unambiguous.

8. Risks and rollout

  • Data impact: none. Read-only, no migration.
  • Backward compatibility: the breaking items in section 5 go in the API README changelog. The only known client is this repo's UI, which is updated in the same branch.
  • /AstronautDuty/{name} side effect: sharing the handler means it also gets 404 and case-insensitivity. This is the correct direction (task 005's notes already asked for a 404 there), but it is visible. The alternative, a separate handler just to keep the old wrong behaviour, adds code for no benefit.
  • Stored values outside the character set: POST /Person and POST /AstronautDuty do not validate yet (tasks 006 and 002). A person or rank stored with, for example, / or & cannot be fetched or filtered by that exact value (400). This is acceptable before go-live; the seed data is clean.
  • Non-ASCII case folding is limited to ASCII (D1c). It is documented and pinned by a test.
  • Performance: the (@p IS NULL OR ...) form and the leading-wildcard LIKE mean a full scan. That is fine at this data size. Revisit with paging.
  • Rollback: revert the merge commit. There is no state to undo.

13. Questions for you

Q1. The injection acceptance criterion versus the character-set rule. The AC says x' OR '1'='1 gets 404 on GET /Person/{name} and an empty list as a name filter. The AC also requires an allowed character set, and = is not in it, so over HTTP that exact string is rejected with 400 before any SQL runs.

Recommendation: keep the character set on all four inputs. Prove parameterisation with the literal string at handler level (404 and empty list). Over HTTP, prove it with apostrophe strings that pass validation (x' OR 'a' LIKE 'a gives an empty list, and a real O'Brien name round-trips). Expect a 400 for the literal string.

Alternative: the route value gets only a length check, so the literal AC holds (404). This weakens input validation, and only the route regex changes in the contract.

Q2. Add Microsoft.AspNetCore.Mvc.Testing (test project only)? It is needed to test 400 validation, URL decoding and Swagger in xUnit.

Recommendation: yes. It is first-party and test-only, and CLAUDE.md names WebApplicationFactory as the integration approach.

If no: controller-level and rule tests stay, and QA covers tier H by hand on every change, so a regression there would not be caught in CI.

Q3. Accept ASCII-only case-insensitivity? élena will not find Élena.

Recommendation: accept and document. The data is ASCII, and task 002's NOCASE unique index will behave the same way. Revisit if non-ASCII names matter.
