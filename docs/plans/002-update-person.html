1. Summary and verdict

This task adds PUT /Person/{personId} with body { "name": "..." }. It renames the person and returns 200 with the person in the existing PersonAstronaut shape. An unknown id returns 404, invalid input returns 400, and a name already used by another person (ignoring ASCII case and surrounding whitespace) returns 409. A new migration makes Person.Name COLLATE NOCASE with a unique index. The migration aborts and changes nothing if duplicates exist. A unique-constraint violation that gets past the pre-check is mapped to 409. The shared name rule in InputRules gets stricter: input is NFC-normalised, invisible letters and marks are rejected, and combining marks are limited. The read side (task 001 endpoints) also NFC-normalises its input. The UI gets StargateApi.updatePerson.

Verdict: multi. The work spans api + db and ui, joined by an HTTP contract. The UI part (one client method, types, Vitest) can be built in parallel against docs/contracts/002/ without waiting for the API. The api and db work stays in one subtask because the 409 path, the migration and the tests depend on each other closely. The UI subtask is small, but parallel work against a written contract is cheap and keeps the monorepo rule (same-commit client update) easy for the lead to integrate.

The problem is real. I checked it on main: there is no update endpoint and no unique index on Person.Name (snapshot StargateContextModelSnapshot.cs:81-94). The only duplicate check (CreatePerson.cs:14-29) is never registered (Program.cs:19-23 registers only CreateAstronautDutyPreProcessor), so duplicates can be created today. The task's assumptions hold, with one correction about the migration (see 4.3): a plain EF-generated migration would not fail cleanly on case-only duplicates.

4. Approach

4.1 Endpoint

  • PUT /Person/{personId}, with [Consumes("application/json")], [RequestSizeLimit(4096)] (Amendment 1b) and body UpdatePersonRequest { [Required, ValidName] string? Name }. The route has no :int constraint (see 4.6). personId is int with [Range(1, int.MaxValue)].
  • The controller is thin: it sends MediatR UpdatePerson { PersonId, Name } and returns this.GetResponse(result). There is no try/catch.
  • Validation order (Amendment 1b): route and body validation run before the handler. So an unknown id with an invalid name gives 400, not 404, and personId 0 with a valid name gives 400 (key personId).
  • Response UpdatePersonResult : BaseResponse { PersonAstronaut? Person }. This keeps the current person shape (task decision) and is the same field layout as GetPersonByNameResult, but it is its own type because task 008 deletes GetPersonByName*. JSON property order is not significant; the server writes person first.
    • 200: person is non-null. It is the same projection as a GET /Person entry (rank and title "" when unassigned, nullable dates).
    • 404: {success:false, message:"Person not found", responseCode:404, person:null}. Also returned if the row is deleted concurrently, either between the load and the save (DbUpdateConcurrencyException, Amendment 1b) or before the read-back (Amendment 1).
    • 409: {success:false, message:"A person with this name already exists", responseCode:409, person:null}. Messages never echo input.
    • 400: the framework's ValidationProblemDetails, the same as task 001.
    • 413 (Amendment 1b): the body is over 4096 bytes, on Kestrel. The response body is unspecified.
    • 415: when the content type is not JSON. (Amendment 1) The body is empty for a non-JSON Content-Type and ProblemDetails when the header is missing. Clients key on the status only.
    • 500: empty body in Production.
  • There is no Location header. A 200 does not need one, and the only by-name route is removed by task 008.
  • Handler steps:
    1. If the raw name is at most InputRules.MaxRawLength (800) characters, name = InputRules.Normalize(request.Name); otherwise name is empty, so the value is never normalised (Amendment 1b). Throw ArgumentException if !InputRules.IsValidName(name). This is a defensive check for non-HTTP callers and is unreachable via HTTP.
    2. Load Person by id (tracked). If it does not exist, return 404.
    3. Pre-check: AnyAsync(p => p.Id != id && EF.Functions.Collate(p.Name, "NOCASE") == name). If one exists, return 409.
    4. Set person.Name = name, then SaveChangesAsync(ct). Catch DbUpdateConcurrencyException and return 404 (Amendment 1b). Catch DbUpdateException ex when SqliteErrors.IsUniqueViolation(ex) and return 409.
    5. Read back the PersonAstronaut by id with a static parameterised Dapper SQL statement (the GET /Person projection plus WHERE a.Id = @PersonId), and return 200. If no row comes back (the person was deleted concurrently, out of band, since there is no delete endpoint yet), return the same 404 as step 2. A 200 never carries a null person.
    It logs personId and the outcome only, never names.
  • Idempotency: the same PUT twice gives the same final row and the same 200 body. Renaming to the person's own name is excluded from the pre-check, and if the value is byte-identical EF issues no UPDATE. A different casing of the person's own name updates the row and succeeds, because a row cannot conflict with itself in the unique index.
  • Renaming only writes Person.Name. AstronautDetail and AstronautDuty are not loaded or written (rule 2 and rules 3-7 are unaffected).

4.2 The shared name rule (InputRules), defined once for 002 and 006

// Business/Validation/InputRules.cs (changed)
public const int MaxLength = 100;
public const int MaxRawLength = 8 * MaxLength; // 800; raw input over this is rejected before normalising (Amendment 1b)
// Default-ignorable code points that Unicode classes as letters (Lo) or marks (Mn) and that render as nothing.
// Written as regex escapes, never as literal characters (28 code points; table in data.md).
private const string Invisible = @"\u034F\u115F\u1160\u17B4\u17B5\u180B-\u180F\u3164\uFE00-\uFE0F\uFFA0";
public const string AllowedCharactersPattern =
    @"^(?:(?![" + Invisible + @"])\p{L}(?:(?![" + Invisible + @"])\p{M}){0,3}|[0-9 .'-])+\z";
public const string AllowedCharactersMessage =
    "Use only letters, digits, spaces, hyphens, apostrophes and periods (at most 100 characters)."; // unchanged
/// NFC, then string.Trim(). Total: ill-formed UTF-16 (lone surrogate) is returned trimmed but not normalised; it then fails the pattern.
public static string Normalize(string value);
/// True when 1 <= normalized.Length <= MaxLength and the pattern matches. Expects the output of Normalize.
public static bool IsValidName(string normalized);

In words, a name is valid when it has at most 800 UTF-16 code units as sent, and, after NFC normalisation and trimming, it has 1 to 100 UTF-16 code units and is a sequence of:

  • a letter (\p{L}) followed by 0 to 3 combining marks (\p{M}), or
  • an ASCII digit, space, period, apostrophe (U+0027) or hyphen,

and contains none of the invisible code points listed above.

The effects of this rule:

  • A mark at the start, or after a digit, space or punctuation, is invalid.
  • Four or more consecutive marks after NFC are invalid. Three covers Thai (vowel plus tone mark) and pointed Hebrew, and stops stacked-mark display abuse.
  • Surrogate pairs (supplementary planes) stay rejected, as on main.
  • \z replaces $, so a trailing \n can never match even in a raw Regex.IsMatch.
  • Use a [GeneratedRegex] (CultureInvariant) or a static Regex with a 100 ms timeout.
  • Writes (this task's PUT and task 006's POST) use the new [ValidName] attribute (Business/Validation/ValidNameAttribute.cs). It rejects raw strings over 800 characters, then validates IsValidName(Normalize(value)). It treats null as valid (pair it with [Required]), and fails on non-strings. Handlers store Normalize(value). NFC is applied in the model-validation step (inside the attribute) and again in the handler before comparing or storing. Both call the same function, so validation and storage cannot drift.
  • Reads (task 001's GET /Person filters and GET /Person/{name}) keep their [StringLength] + [RegularExpression(AllowedCharactersPattern)] attributes. They pick up the new pattern automatically, applied to the raw value. GetPeople and GetPersonByName handlers replace Trim() with InputRules.Normalize(), so NFD input finds NFC-stored names. One edge case differs from writes: a raw query with 4 or more marks that NFC would compose down to 3 gets a 400 on read. That is harmless.
  • Contract impact on task 001 endpoints: non-breaking for ASCII. It is stricter for non-ASCII input with invisible letters or marks, a leading or stray mark, or 4 or more stacked marks (now 400 instead of 200 with no match). NFD input now matches NFC names. The 400 shape, the keys and the message are unchanged. The pattern string shown in Swagger for those parameters changes.
  • Case folding stays ASCII-only (SQLite NOCASE). Émile and émile are distinct names. This matches the ASCII-only decision accepted in task 001, and it is a documented limit of rule 1 for non-ASCII letters.

4.3 Database

  • Model change (PersonConfiguration): builder.Property(x => x.Name).UseCollation("NOCASE"); and builder.HasIndex(x => x.Name).IsUnique();, which gives the index IX_Person_Name.
  • The new migration is generated with dotnet ef migrations add AddUniquePersonNameIndex -o Business/Migrations --namespace StargateAPI.Migrations. It updates the snapshot. Existing migrations are not touched.
  • Trim set (Amendment 1b): the migration declares public const string TrimCharacterCodes, the 25 code points for which char.IsWhiteSpace is true. These are exactly what string.Trim() removes in the API, and test M9 asserts the equality. Below, char(T) means char(TrimCharacterCodes).
  • Up runs, in this order:
    1. Guard (migrationBuilder.Sql, the same temp-table and trigger pattern as task 003). It runs RAISE(ABORT) when SELECT 1 FROM main."Person" GROUP BY trim("Name", char(T)) COLLATE NOCASE HAVING COUNT(*) > 1 finds a row, or (Amendment 1b) when any trim("Name", char(T)) = ''. The exact message is in data.md.
    2. Trim: UPDATE "Person" SET "Name" = trim("Name", char(T)) WHERE "Name" <> trim("Name", char(T)).
    3. The generated AlterColumn (rebuild with COLLATE NOCASE) and CreateIndex.
    The guard and the trim run in the first transaction, before EF's rebuild commits anything. If the guard aborts, nothing is committed (verified in probe 2). The guard uses the same trim set and collation that the index sees after the trim, so the later index creation cannot fail on duplicates.
  • Why column collation and not an index-only COLLATE NOCASE via raw SQL: collation on the column is part of the EF model, so any future SQLite table rebuild re-creates it. An index-only collation written in raw SQL would be silently dropped to BINARY by the next EF rebuild of Person. It also makes every = on Name, in EF and in Dapper, case-insensitive by default.
  • Down is generated: it drops IX_Person_Name and rebuilds without the collation. Trimmed names stay trimmed. That is not reversible and does no harm.
  • Existing rows are not NFC-normalised. SQLite cannot do it in SQL, and a C# data step does not belong in a schema migration. The dev seed is ASCII. This is a documented residual risk (see 9).
  • The seeded Development DB (task 004) has six distinct ASCII names, so it migrates cleanly. On the next dotnet run in Development, the initializer applies the pending migration.

4.4 Concurrency

The pre-check gives a fast 409 in the common case. The unique index is the guarantee. A rename that loses a race gets DbUpdateException with an inner SqliteException { SqliteErrorCode: 19, SqliteExtendedErrorCode: 2067 }, which the handler maps to 409. Any other database error (for example an FK violation, 787) is not mapped and stays a 500. The predicate lives in Business/Data/SqliteErrors.cs (IsUniqueViolation(DbUpdateException)) so that task 006 can reuse it. It is SQLite-specific and transitional, like StarbaseDatabase. A concurrent delete maps to 404, at either point (4.1).

4.5 UI

StargateApi.updatePerson(personId: number, name: string): Observable<UpdatePersonOutcome> sends PUT /api/Person/{personId} with body { name } exactly as given (the server normalises it). It maps the response as follows:

  • 200 maps to {status:'updated', person}.
  • 404 maps to {status:'notFound'}.
  • 409 maps to {status:'conflict'}.
  • 400 maps to {status:'invalid', errors}.
  • Any other error propagates, including 413 and 415.

This follows getPerson, which already maps 404 to null, and gives a future edit form a typed result. There is no screen.

4.6 Smaller decisions

  • No route constraint on {personId}. With {personId:int}, PUT /Person/abc would match GET /Person/{name} by path and return 405 until task 008, which is confusing. Without it, binding fails and returns 400.
  • The framework's binding message "The value 'abc' is not valid..." echoes input. Override it globally with five ModelBindingMessageProvider accessors:
    • SetAttemptedValueIsInvalidAccessor((_, _) => "The value is not valid.")
    • SetValueIsInvalidAccessor(_ => "The value is not valid.")
    • SetValueMustBeANumberAccessor(_ => "The value must be a number.")
    • (Amendment 1) the non-property variants, SetNonPropertyAttemptedValueIsInvalidAccessor(_ => "The value is not valid.") and SetNonPropertyValueMustBeANumberAccessor(() => "The value must be a number."). Action parameters such as personId use these, and without them /Person/99999999999 still echoes the value.
    These apply only to non-body binding (route, query). All existing route and query parameters are strings, so no current response changes.
  • The GetPersonByName exact-case tie-break SQL becomes dead (no case duplicates can exist). It is left unchanged, because task 008 deletes the file. Only its input normalisation changes.

Main alternative rejected

Normalise the stored key in a second column (NameKey = lower(NFC(trim(Name))) with a unique index). This would give Unicode-aware case folding in C#. I rejected it for three reasons. It adds a column, a backfill that must run in C# (data migration) and a sync obligation on every writer, including the external feed. It contradicts the accepted ASCII-only decision. The task asks for a unique case-insensitive index on Person.Name. Raw-SQL index-only collation was also rejected (see 4.3).

7. Domain rules

  • Rule 1 (Name unique) is enforced in code (normalise, then the pre-check with NOCASE) and in the database (unique index on a NOCASE column, plus the 2067 to 409 mapping). Equality is ASCII-case-insensitive after NFC and trim. The migration and the API trim the same whitespace set. Limits: non-ASCII case variants are distinct, existing non-NFC rows are not rewritten, and POST does not trim until task 006.
  • Rule 2 (no assignment means no astronaut rows): renaming never creates or touches AstronautDetail or AstronautDuty. Tests compare dumps of both tables before and after.
  • Rules 3-7: not touched. Person-related rows keep their PersonId, because the rebuild keeps Id and the FKs reference Person by name.

9. Risks and rollout

  • Data: the migration trims padded names (Q1) and otherwise changes no data. If case or whitespace duplicates exist, or a name is empty once trimmed, it aborts with nothing changed and tells the operator how to find them. Any real data needs a backup first (already in the README).
  • Residual rule-1 gaps, documented:
    • Non-ASCII case variants are distinct names.
    • Pre-existing NFD-stored names are not rewritten.
    • Until task 006, POST /Person stores untrimmed names, so "Ada " can still be created next to Ada, and a later rename to Ada is not blocked by such a row. Duplicate POSTs that differ only in case now return 500 instead of creating a duplicate (Q2).
  • Backward compatibility: the PUT is additive. The read side is unchanged for ASCII.
  • Rollback: dotnet ef database update MakeCareerStartDateRequired runs Down, and reverting the commit removes the endpoint. Trimmed names are not restored (harmless).
  • Partial-apply risk: EF warns that the rebuild "cannot be executed in a transaction" (seen in probe 2; the same applies to task 003). The guard runs before the first commit and guarantees the final index succeeds, so the only remaining risk is a crash in the middle of the rebuild, which is inherent to SQLite.
  • Unverified (each has a cheap check; the lead must confirm before merge):
    1. The ModelState key for an invalid body name is Name. Check: the first HTTP 400 test. Tests compare the key case-insensitively.
    2. Resolved by Amendment 1: the prediction that a wrong Content-Type gives 415 with a ProblemDetails body was wrong. A non-JSON Content-Type is rejected by endpoint routing with an empty body. Only a missing Content-Type gets ProblemDetails. The contract now guarantees the status only.
    3. Through EF, the DbUpdateException.InnerException is the SqliteException with code 2067. Probe 3 verified this on raw ADO only. Check: the interceptor handler test.
    4. Parallel PUTs on one SQLite file do not surface SQLITE_BUSY (default 30 s busy timeout). Check: the concurrent HTTP test, run 20 times locally.
    5. The binding-message override does not change any existing response. Check: the full existing test suite stays green.
    6. Resolved by Amendment 1b: SQLite trim(x, char(...)) with the 25-code-point list trims every whitespace character at both ends. M10 covers this.
    7. (1b) A body over 4096 bytes gets 413 on real Kestrel. TestServer does not enforce [RequestSizeLimit]. Check: QA step 10.

13. Questions for the user

  1. Q1: Trim existing names in the migration? This alters data in rows with padded names. CLAUDE.md asks for approval before doing that. Recommendation: yes. It matches the "names are trimmed before stored" decision. It only runs after the guard proves no collision and no name that is empty once trimmed. The trim set is the 25 Unicode whitespace characters the API trims (Amendment 1b). The alternative is for the guard to also abort on any padded name, which forces manual cleanup.
  2. Q2: Accept the interim POST /Person behaviour until 006? Case or exact duplicates give a generic 500, and padded names still insert. Recommendation: accept. 006 owns POST and depends on this task.
  3. Q3: Combining-mark limits. A mark must follow a letter, with at most 3 in a row after NFC. Recommendation: accept. This covers real names in Latin, Thai, Indic and pointed Hebrew scripts.
