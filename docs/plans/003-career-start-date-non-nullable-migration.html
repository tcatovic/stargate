Verdict: simple, implemented by api-dev only.

All the work is in the API project and its migrations (the "db" platform here is just EF migrations inside exercise1/api), plus a new test project and two README files. There is no HTTP contract change and no UI change. The subtasks depend on each other in order (migration, then path resolution, then tests, then docs), so parallel agents would not help. No contracts folder is written.

The task's premise is correct. The one drift is CareerStartDate, and the snapshot's ProductVersion is 7.0.15. One part of the premise is narrower than stated: dotnet ef and dotnet run already resolve to the same file. The real divergence is running the built binary directly (see section 3).

The plan:

  • Migration. Add one migration, MakeCareerStartDateRequired. Remove the defaultValue backfill that the scaffolder adds. Add a guard in Up that aborts with a clear message when NULLs exist. Keep the scaffolded Down.
  • Database path. Bake the API project folder into the assembly at build time. Resolve any relative Data Source against that folder in one helper, called from Program.cs.
  • Docs. Document the database procedure in exercise1/api/README.md and link it from exercise1/README.md.
  • Tests. Create exercise1/api.Tests (xUnit). This needs the user's approval to add packages.

4. Approach and decisions

4a. Migration (decided)

Generate the migration with the tool so the snapshot and Designer file are produced by EF, not written by hand:

cd exercise1/api
dotnet ef migrations add MakeCareerStartDateRequired -o Business/Migrations --namespace StargateAPI.Migrations

Use --namespace StargateAPI.Migrations to match InitialCreate and the snapshot. Without it, the tool emits StargateAPI.Business.Migrations. The tool rewrites the snapshot: CareerStartDate becomes DateTime and ProductVersion becomes 10.0.13. That is the only semantic change. The existing files use CRLF and the regenerated snapshot uses LF (per .editorconfig), so the git diff shows a whole-file rewrite. Reviewers should use git diff --ignore-cr-at-eol.

Then edit the new migration's Up (this needs the hook question resolved first):

  1. Delete the line defaultValue: new DateTime(1, 1, 1, 0, 0, 0, 0, DateTimeKind.Unspecified),. This removes the silent IFNULL(..., '0001-01-01') backfill.
  2. Insert this guard before the AlterColumn call. This exact form was verified:
// No backfill (task 003): abort, changing nothing, if any row lacks a CareerStartDate.
// SQLite has no RAISE outside triggers, so a temp trigger on a temp table raises the error.
migrationBuilder.Sql(
    """
    CREATE TEMP TABLE "__guard_CareerStartDate" ("x" INTEGER);
    CREATE TEMP TRIGGER "__guard_CareerStartDate_check" BEFORE INSERT ON "__guard_CareerStartDate"
    WHEN EXISTS (SELECT 1 FROM main."AstronautDetail" WHERE "CareerStartDate" IS NULL)
    BEGIN
        SELECT RAISE(ABORT, 'MakeCareerStartDateRequired: AstronautDetail has rows with NULL CareerStartDate. No data was changed. Delete starbase.db and run dotnet ef database update, or set CareerStartDate on those rows first.');
    END;
    INSERT INTO "__guard_CareerStartDate" ("x") VALUES (1);
    DROP TABLE "__guard_CareerStartDate";
    """);

Down stays as scaffolded: AlterColumn back to nullable: true. The SQL is constant, with no interpolation, so it complies with the "no interpolated SQL" rule.

Why the failure is atomic. EF puts the guard in the same transaction as the creation of ef_temp_AstronautDetail and the row copy. RAISE(ABORT) stops the run before any later statement. The transaction rolls back, which removes the temp objects. The history row is never written. This was verified on a database with a NULL row.

Alternatives rejected.

  • Only remove defaultValue and rely on NOT NULL. The failure is atomic, but the message (NOT NULL constraint failed: ef_temp_AstronautDetail.CareerStartDate) fails the "clear message" criterion.
  • Temp table with a named CHECK constraint. This works in principle, but the message is limited to a constraint name. I did not test it.
  • A C# pre-check. Up only builds operations. It cannot query data, and it would not work in migrations script output.
  • Hand-writing the SQL table rebuild. This duplicates EF's rebuild and risks a snapshot mismatch.

4b. Connection string resolution (decided: one mechanism)

Mechanism. The API project folder is baked into the assembly at build time. One helper resolves any relative SQLite Data Source against it, and Program.cs calls that helper. dotnet ef runs Program.cs's host (verified), so both tools go through the same code path.

  • StargateAPI.csproj: add <AssemblyMetadata Include="StargateApiProjectDirectory" Value="$(MSBuildProjectDirectory)" /> in an ItemGroup.
  • New exercise1/api/Business/Data/StarbaseDatabase.cs, a public static class StarbaseDatabase with:
    • public const string ConnectionStringName = "StarbaseApiDatabase";
    • public const string DefaultConnectionString = "Data Source=starbase.db";
    • public static string ProjectDirectory { get; }, which reads the StargateApiProjectDirectory AssemblyMetadataAttribute from typeof(StarbaseDatabase).Assembly. If the attribute is missing, it throws InvalidOperationException. No !.
    • public static string ResolveConnectionString(string? configured, string baseDirectory), a pure function (tested directly):
      1. If configured is null or whitespace, use DefaultConnectionString. This covers the run-the-dll case where appsettings.json is not under the content root.
      2. Parse with SqliteConnectionStringBuilder.
      3. Leave the string unchanged if DataSource is empty, :memory:, Mode=Memory, or already rooted (Path.IsPathRooted).
      4. Otherwise set DataSource = Path.GetFullPath(Path.Combine(baseDirectory, dataSource)).
      5. If the resulting directory does not exist, throw InvalidOperationException("Database directory '{dir}' does not exist. Set ConnectionStrings__StarbaseApiDatabase to an absolute path."). This prevents a stray empty file being created elsewhere, for example in a published build where the baked folder is absent.
      6. Return builder.ToString(). Other keywords such as Cache and Pooling are kept.
  • Program.cs:13-14 becomes options.UseSqlite(StarbaseDatabase.ResolveConnectionString(builder.Configuration.GetConnectionString(StarbaseDatabase.ConnectionStringName), StarbaseDatabase.ProjectDirectory)).

Override. Standard configuration precedence applies: appsettings.json, then appsettings.{Env}.json, then user-secrets in Development, then the environment variable ConnectionStrings__StarbaseApiDatabase, then the command line (--ConnectionStrings:StarbaseApiDatabase=...). An absolute path is used as is. A relative override is still anchored to the project folder. dotnet ef ... --connection "..." bypasses Program.cs for that one command; the docs say so.

Alternatives rejected.

  • ContentRootPath. It is the project folder under dotnet run and dotnet ef, but it is the current directory when the built dll or apphost is run directly (verified). It fails the "whatever directory" criterion.
  • AppContext.BaseDirectory. It points at bin/Debug/net10.0, so the database would end up in build output.
  • IDesignTimeDbContextFactory. It only affects dotnet ef, which already uses the project folder. It would create a second resolution path that can drift from runtime. That is exactly the "dotnet ef uses the design-time path" risk.

Do not add a design-time factory. If one is ever added, it must call StarbaseDatabase.ResolveConnectionString.

Trade-off. The absolute build-machine path is embedded in the assembly. This is low sensitivity (a developer folder path). It is noted for the security reviewer, and deployments must set an absolute path.

9. Risks and rollout

  • Data impact. On a development database with NULL CareerStartDate rows, the migration refuses to run, by design. The remedy is to reset. There is no production database. Committed data: none (the *.db files are gitignored).
  • Partial-failure window. The rebuild spans three transactions. A crash between (1) and (2) could leave ef_temp_AstronautDetail behind. This is very unlikely on a local file. The recovery is the documented reset.
  • File not byte-identical after a failed run. EF's __EFMigrationsLock row is inserted and then deleted. The data is unchanged, which is what the acceptance criterion asks.
  • The protect-files hook blocks editing the newly scaffolded migration (see the questions). Do not work around it by deleting and recreating the file.
  • Embedded build path in the assembly metadata: low sensitivity. Deployments must set an absolute path, and they fail fast if they don't.
  • Backward compatibility. No API change. A relative Data Source now anchors to the project folder. Anyone relying on a cwd-relative file (for example a starbase.db at the repo root) will see a different, empty database until they migrate. The README calls this out.
  • Rollback. First run dotnet ef database update 20240122154939_InitialCreate (Down verified), then revert the commit. Alternatively, delete starbase.db.
  • Downstream. Tasks 002 and 004 build on this clean chain. Their migrations must also be generated with --namespace StargateAPI.Migrations.
