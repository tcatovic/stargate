1. Summary and verdict

Verdict: simple (one api-dev agent, no contracts folder).

All changes live in exercise1/api and exercise1/api.Tests: one new startup class, one seed-data class, three lines in Program.cs, removal of dead code in StargateContext, tests and README. The task lists db as a platform, but there is no schema change and no new migration; the "db" work is applying the existing chain and inserting rows from C#. No HTTP request/response shape changes, no UI change, so there is nothing for parallel agents to agree on and nothing to split.

The problem is real: Program.cs never touches the database schema, api/README.md:12 tells developers to run dotnet ef database update by hand, and a fresh database has no rows. The commented-out SeedData (StargateContext.cs:22-24, 27-67) uses DateTime.Now and would violate rule 4/5 bookkeeping if enabled. No wrong assumption in the task.

3. Approach and decisions

D1. Where it runs

A new class DevelopmentDatabaseInitializer (Business/Data/DevelopmentDatabaseInitializer.cs), registered scoped, resolved once in Program.cs after builder.Build() and before app.Run(), so the app never serves a request against an unmigrated or half-initialised database:

builder.Services.AddScoped<DevelopmentDatabaseInitializer>();
var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    await scope.ServiceProvider.GetRequiredService<DevelopmentDatabaseInitializer>().InitializeAsync();
}

Placement after Build() matters: dotnet ef loads Program through the host factory resolver, which stops the app when the host is built, so design-time commands (migrations add, database update) never trigger the initializer even though they default to the Development environment. (Unverified, see U1.)

D2. Public shape (the developer must use these names)

public sealed class DevelopmentDatabaseInitializer(
    StargateContext context,
    IHostEnvironment environment,
    ILogger<DevelopmentDatabaseInitializer> logger)
{
    public Task<DatabaseInitializationResult> InitializeAsync(CancellationToken cancellationToken = default);
}

public sealed record DatabaseInitializationResult(
    bool Ran,                                  // false when not Development
    IReadOnlyList<string> AppliedMigrations,   // ids applied by this run, empty if up to date or not run
    bool Seeded);                              // true only when this run inserted the seed

public static class DevelopmentSeedData
{
    public static IReadOnlyList<Person> People();   // a fresh entity graph on every call, Ids unset
}

The environment check is inside the initializer (not around the call in Program.cs) so "not executed outside Development" is unit-testable without WebApplicationFactory. Detection is environment.IsDevelopment() (the standard ASPNETCORE_ENVIRONMENT/DOTNET_ENVIRONMENT value, case-insensitive), same as the existing Swagger switch.

D3. Algorithm

  1. If not Development: log Information "Environment {Environment} is not Development; automatic migration and seeding skipped", return (false, [], false). Do not open a connection (so no database file is created).
  2. pending = await context.Database.GetPendingMigrationsAsync(ct), then await context.Database.MigrateAsync(ct). Log "Applied {Count} migration(s) to {DataSource}: {Migrations}" or "Database {DataSource} is up to date; no migrations applied".
  3. Seed in one explicit transaction: BeginTransactionAsync; if (await context.People.AnyAsync(ct)) log "Seeding skipped: database already holds {PeopleCount} people", roll back, return; else AddRange(DevelopmentSeedData.People()), one SaveChangesAsync, CommitAsync; log "Seeded {PeopleCount} people, {DetailCount} astronaut details and {DutyCount} duties". The emptiness check is inside the transaction so a second concurrent process fails (SQLite busy) instead of inserting duplicates.
  4. {DataSource} is new SqliteConnectionStringBuilder(context.Database.GetConnectionString()).DataSource. Never log the full connection string.

D4. Failure behaviour

Any exception in step 2 or 3 is logged at Critical ("Development database initialization failed during {Step} for {DataSource}") and rethrown wrapped as InvalidOperationException with message "Development database initialization failed during migration|seeding for '<path>'. No seed data was written. See exercise1/api/README.md (Troubleshooting, Reset)." and the original as InnerException. Program.cs does not catch it: the process exits non-zero and the runtime prints the message, so the app never starts serving. A seeding failure rolls back the transaction (nothing seeded); the schema stays migrated, and the next start retries seeding because Person is still empty. Migration and seeding are deliberately not one transaction (EF manages migration transactions itself, and the 003 migration toggles PRAGMA foreign_keys, which cannot run inside one).

D5. Seeding approach

Rows inserted directly via EF (Person graphs with AstronautDetail and AstronautDuties navigation), not through CreateAstronautDutyHandler. Dates are fixed new DateTime(y, m, d) (date-only, no DateTime.Now). Ids are not set; SQLite assigns them. Idempotency rule: seed only when Person is empty. The commented-out SeedData method and its call are deleted from StargateContext (model unchanged; Model_has_no_pending_changes_against_the_migration_chain keeps guarding this).

Alternatives rejected

  • EF Core 9+ UseSeeding/UseAsyncSeeding on the DbContextOptions: it also runs on every Migrate() and on dotnet ef database update, including against non-Development databases and inside the existing TestDatabase.Migrate tests, and it gives no single place for the Development gate, logging and the fail-to-start policy. Main alternative, rejected.
  • HasData in OnModelCreating: bakes fixed Ids and sample people into a migration that would ship to every environment, and needs a new migration; violates "nothing runs outside Development".
  • An IHostedService: runs concurrently with Kestrel start in some configurations and complicates fail-to-start; a scoped call before Run() is simpler.
  • WebApplicationFactory<Program> tests: would need a new package (Microsoft.AspNetCore.Mvc.Testing) and, because the factory defaults to Development, would run the initializer against whatever database it is pointed at. Testing the class directly covers every acceptance criterion except the three-line Program.cs wiring, which QA covers end to end. See Q2.

8. Tests

All in exercise1/api.Tests, each on its own TestDatabase file (never starbase.db). Initializer built directly: new DevelopmentDatabaseInitializer(db.CreateContext(), fakeEnv, logger).

DevelopmentDatabaseInitializerTests

  1. Missing file, Development: Given no file at db.Path, when initialized, then Ran, AppliedMigrations equals both migrations in order, Seeded is true, db.AppliedMigrations() is complete, Person count is 6.
  2. Out-of-date, empty: Given db.Migrate(InitialCreate), when initialized, then AppliedMigrations == [LatestMigration], CareerStartDateIsNotNull(), seeded.
  3. Up to date, empty (as left by 003's dotnet ef database update): no migrations applied, seeded.
  4. Idempotent: run twice on the same file; second result ([], Seeded=false); Dump() identical before and after; counts 6/4/8.
  5. Skipped when people exist: Given migrated db with one person "Ada", when initialized, then Seeded false, Person count 1, detail and duty counts 0.
  6. Not Development (Theory: Production, Staging, Test): Given no file, when initialized, then Ran false and File.Exists(db.Path) is false. Second case: Given db.Migrate(InitialCreate), then history is still only InitialCreate and Person count 0.
  7. Development detection is case-insensitive: "development" runs.
  8. Seeding failure rolls back (hostile DB): Given a migrated db with CREATE TRIGGER fail_seed BEFORE INSERT ON AstronautDuty WHEN NEW.DutyTitle = 'RETIRED' BEGIN SELECT RAISE(ABORT, 'seed boom'); END;, when initialized, then it throws InvalidOperationException whose message contains "seeding" and the data source path, the inner chain contains "seed boom", and Person, AstronautDetail and AstronautDuty counts are all 0. Then drop the trigger, initialize again: seeded (retry works).
  9. Migration failure fails start: Given the 003 scenario (InitialCreate, one person, a detail with NULL CareerStartDate), when initialized, then it throws InvalidOperationException with "migration" in the message and the 003 guard text ("NULL CareerStartDate") in the inner chain; history is still only InitialCreate; no seed rows (Person count still 1).
  10. Logging: with the capturing logger, a fresh run logs Information entries for migrations applied (count 2) and seeding ran; a second run logs "no migrations applied" and "Seeding skipped"; the failure test logs one Critical entry. Assert on level and key words, not exact text. No entry contains "Data Source=" (connection string never logged).
  11. Cancellation: an already-cancelled token throws OperationCanceledException and leaves no seed rows.

SeedDataRulesTests (independent of the seeder's constants)

Seed a fresh TestDatabase through the initializer, then assert only with SQL through db.Scalar/db.Strings (never by reading DevelopmentSeedData):

  1. Rule 1: no duplicate names (case-insensitive).
  2. Rule 2: at least one person with no detail and no duties; detail exists iff duties exist.
  3. Rules 3/4: per astronaut exactly one DutyEndDate IS NULL, and it has the max start.
  4. Rule 5: every non-last duty ends the day before the next starts (LEAD window query); at least one person has 3 or more duties.
  5. Rules 6/7: at least one person currently RETIRED; their CareerEndDate = retired start minus 1 day; every non-retired detail has null CareerEndDate.
  6. Coverage: at least two people with exactly one duty and a null end date.
  7. Detail agrees with current duty (rank, title) and CareerStartDate = MIN(DutyStartDate).
  8. Date-only: every stored date ends in 00:00:00.
  9. Deterministic: two fresh databases seeded separately have identical Dump() output.

Existing tests (MigrationTests, StarbaseDatabaseTests, including Model_has_no_pending_changes... and Test_databases_live_under_the_temp_folder...) must keep passing. Build: the API still has the 6 known nullability warnings (task 005), so build the API with plain dotnet build and confirm the count stays 6 (no new warnings); the test project already has TreatWarningsAsErrors and must stay clean.

10. Risks and rollout

  • Data impact: Development only. An existing developer starbase.db with people is never modified by seeding; an empty one gets the six sample people. A database pending the 003 migration is now migrated at startup (same migration and guard as dotnet ef database update; it already aborts without changing data on NULL rows).
  • Behaviour change: a broken Development database now stops the app at startup instead of failing on the first request. Intended; documented in README Troubleshooting.
  • Future integration tests: WebApplicationFactory defaults to Development, so the initializer will run there. Those tests must point the context at a TestDatabase (they get a migrated, seeded db, which is useful) and must never reach starbase.db.
  • Future validation: if a later task restricts ranks/titles to an allowed list, the seed must conform; the rules test does not check that.
  • Concurrency: two Development instances on one file: EF's migration lock serialises migrations; the seeding transaction makes the second writer fail with SQLITE_BUSY rather than duplicate. Acceptable for Development.
  • Rollback: revert the commit. No schema or data migration to undo; seeded rows in developer databases are disposable (reset per README).
