1. Summary and verdict

Verdict: simple. One api-dev agent does the work, with no contracts folder.

The changes are:

  • three nullable annotations;
  • two null guards in handler code that no request reaches today;
  • a new exercise1/Directory.Build.props;
  • one line removed from the test csproj;
  • a few unit tests;
  • a README build note.

All of it is in exercise1/api and exercise1/api.Tests. Schema, migrations, controllers, pre-processors, the UI and every HTTP response stay unchanged. There is nothing to split into parallel work.

The problem is real. A clean build of the baseline (dotnet build --no-incremental, SDK 10.0.402) reports exactly the 6 warnings listed in the task and 0 errors, all in StargateAPI.csproj. api.Tests has no warnings of its own and already sets TreatWarningsAsErrors in its own csproj. StargateAPI.csproj does not, so a plain dotnet build passes with warnings.

I built a prototype in a scratch copy, with the same annotations and props file and an equivalent guard. Results:

  • 0 warnings, and -warnaserror passes;
  • all 61 existing tests pass;
  • dotnet ef migrations has-pending-model-changes reports "No changes have been made to the model since the last migration";
  • TreatWarningsAsErrors resolves to true in both projects;
  • a deliberate CS0168 fails a plain build.

Nothing was left in the repo.

2. Task assumptions checked

Two things in the task do not match the code, and both support the reduced scope.

  • The duties GET route does not run the duties handler. GET /AstronautDuty/{name} sends GetPersonByName (Controllers/AstronautDutyController.cs:24), not GetAstronautDutiesByName. I ran it on the seeded Development database: an unknown name returns 200 {"person":null,"success":true,"message":"Successful","responseCode":200}, not a 500. Nothing reaches GetAstronautDutiesByNameHandler today, so warnings 4 and 5 are in dead code.
  • POST with an unknown person returns 400, not a NullReferenceException. POST /AstronautDuty with an unknown person is rejected by CreateAstronautDutyPreProcessor (Business/Commands/CreateAstronautDuty.cs:33-35), which throws BadHttpRequestException. I ran it in Development: the response is 400 and the body is the developer exception page (a stack trace). The handler's null dereference (:60, warning 6) is reached only if the pre-processor is bypassed. No request can do that today.

So the guards below only satisfy the compiler. They change no observable behaviour. The duties task owns the real behaviour of both endpoints.

4. Approach and decisions

D1. Navigation properties: Person?, not required (warnings 1 and 2)

AstronautDetail.Person and AstronautDuty.Person become public virtual Person? Person { get; set; }. This is accurate: entities read through Dapper, or through AsNoTracking without Include, really do have a null navigation.

The relationship stays required. EF takes requiredness from the non-nullable int PersonId foreign key, not from the navigation. I checked this in the scratch copy: has-pending-model-changes reports no changes and the snapshot is unchanged.

Rejected: required Person Person.

  • Every new AstronautDetail { ... } and new AstronautDuty { ... } would then have to set Person, or fail with CS9035. That includes CreateAstronautDuty.cs:66 and :100, DevelopmentSeedData and the tests.
  • It would also promise something Dapper reads do not deliver.

D2. GetAstronautDutiesByNameResult.Person becomes PersonAstronaut? (warning 3)

This matches GetPersonByNameResult and the UI type person: PersonAstronaut | null (ui/src/app/api/models.ts:35). The JSON name and type stay the same.

D3. Smallest guard in GetAstronautDutiesByNameHandler (warnings 4 and 5). No request reaches this today.

Insert this straight after the first query (:30), before result.Person = person;:

if (person is null)
{
    return result;
}

The returned result has Person = null and an empty AstronautDuties list. It keeps the BaseResponse defaults (Success=true, "Successful", 200), which is what the existing person lookup also returns for an unknown name.

There is deliberately no 404 here. Choosing the status for an unknown name belongs to the duties task, and nothing calls this handler today (section 2). Writing the null check as an early return also fixes warning 4 without a separate change.

D4. Smallest guard in CreateAstronautDutyHandler (warning 6). No request reaches this today.

Insert this straight after the person lookup (:58), before the line at :60:

if (person is null)
{
    return new CreateAstronautDutyResult
    {
        Success = false,
        Message = "Person not found",
        ResponseCode = (int)HttpStatusCode.NotFound
    };
}
  • System.Net is already imported.
  • The message is fixed and does not echo the name.
  • Nothing is written: the guard returns before any Add or SaveChangesAsync.
  • The pre-processor stays unchanged and still rejects every unknown name with 400 before the handler runs. This branch is a defensive guard only, and HTTP behaviour stays exactly as today.
  • The handler's interpolated lookup at :56-58 is left as it is. See the known risk in section 10.

D5. exercise1/Directory.Build.props

<Project>
  <!-- Every .NET project under exercise1/ fails the build on any warning (CLAUDE.md: warnings as errors). -->
  <PropertyGroup>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <!-- NuGet audit results come from an external feed that changes without a commit (NU1900 = feed unreachable,
         NU1901-NU1904 = low..critical advisory). They are still reported as warnings, but must not break every
         branch the day an advisory is published or the feed is offline. Gate them in CI instead. -->
    <WarningsNotAsErrors>$(WarningsNotAsErrors);NU1900;NU1901;NU1902;NU1903;NU1904</WarningsNotAsErrors>
  </PropertyGroup>
</Project>
  • Scope. MSBuild uses the nearest Directory.Build.props above each project, and there is none in the repo today. Both api and api.Tests inherit this file, and so will any future project. exercise1/ui is not an MSBuild project and is not affected. I checked with dotnet msbuild -getProperty:TreatWarningsAsErrors: it prints true for both projects.
  • Test csproj. Remove the duplicate <TreatWarningsAsErrors>true</TreatWarningsAsErrors> from StargateAPI.Tests.csproj:8, so the setting lives in one place.
  • -warnaserror on the command line. The SDK copies WarningsNotAsErrors into MSBuildWarningsNotAsErrors; I checked this with -getProperty. So dotnet build -warnaserror, the CLAUDE.md command, honours the same exception list. I have not yet seen a real advisory stay a warning under it (section 12).
  • Why this is not a suppression. No compiler warning is exempt and NoWarn is untouched. Audit findings still print. The only thing excluded from failing the build is supply-chain data that changes without any commit.
  • Rejected: NU190x as errors. A newly published advisory, or the sandbox firewall blocking the audit feed (NU1900), would break every build on every branch with no change in the repo.
  • dotnet ef and design-time builds. dotnet ef builds the project first, so a warning will now block migrations add and database update. That is intended. Scaffolded migrations compile cleanly: both existing ones do, and they carry #nullable disable. IDE design-time builds will also show warnings as errors.
  • SDK roll-forward. global.json pins 10.0.100 with latestFeature, and the sandbox runs 10.0.402. A newer SDK that adds analyzer warnings will fail the build until those warnings are fixed. That is the policy working as intended, and the README will say so.

10. Risks and rollout

  • Data. None. There is no migration, the model is unchanged (checked), and no row is touched.
  • Behaviour. None is observable. The guards sit in paths no request reaches, and every endpoint keeps its current responses.
  • Known, unchanged risk: SQL injection in the duty handlers. This task does not introduce it, does not widen it, and does not fix it. Both handlers, and GetPersonByName, still build SQL from the name by string interpolation (GetAstronautDutiesByName.cs:28, CreateAstronautDuty.cs:56, GetPersonByName.cs:26). The pre-processor is unchanged, so CreateAstronautDutyHandler's interpolated lookup is reached only for names that an EF parameterised query has already matched to a real person, exactly as today. GetPersonByName stays reachable with any input over HTTP, as today. Fixing it is owned by task 001 (GetPersonByName) and the duties task (both duty handlers).
  • Other branches. After this merges, any branch for 001, 002 or 006 that adds warnings will fail to build. That is intended: per the task, those branches must fix their warnings, not suppress them. Merge this one first. Expect small conflicts with the duties task in the two handler files, where it replaces the guards anyway.
  • Supply chain. NU190x stay warnings (D5). Until CI exists, a new advisory shows up only as a build warning. Recommended follow-up: a CI step that runs dotnet list package --vulnerable --include-transitive and fails on high or critical findings.
  • Rollback. Revert the commit. Nothing persists outside the code.

11. Deferred to the duties task

These items were in revision 1 and are not built in 005. They are recorded so they are not lost.

  • GET 404 over HTTP. GET /AstronautDuty/{name} should return 404 with a BaseResponse body when the name is unknown (responseCode equal to the HTTP status). That needs the controller rewired from GetPersonByName to GetAstronautDutiesByName (AstronautDutyController.cs:24). The success response then gains astronautDuties, which is an additive shape change. The UI types already expect it (models.ts:34-37), but it is still a contract change to record.
  • POST 404 over HTTP. POST /AstronautDuty for an unknown person should return 404 with a BaseResponse body instead of 400 and a stack trace. A pre-processor cannot return a response, so either the unknown-person check moves into the handler, or a global exception handler maps a not-found exception to ProblemDetails, which CLAUDE.md prefers. If the pre-processor stops rejecting unknown names, the handler's person lookup must be parameterised first. Otherwise a name such as x' OR '1'='1 would match an existing person and write a duty to them. This is a breaking status change (400 to 404) and needs a changelog entry.
  • Lookup order. An unknown person should get 404 before the duplicate check (title plus start date) runs. The current duplicate check is also global rather than per person.
  • Names with apostrophes. A real name containing ' passes the pre-processor today but breaks the handler's interpolated SQL, giving a 500 (expected from the code; not run). This goes away once the lookup is parameterised.
  • Behaviour tests. Unknown name, hostile names, a colliding duty for an unknown person, the success path through the MediatR pipeline, the duplicate-duty 400, HTTP status equal to responseCode at the controller, and the apostrophe name. Each POST test should compare database dumps before and after.
  • Remove the interim guards. The guards added in D3 and D4 are interim. The duties task replaces them with the real behaviour.
