1. Summary and verdict

Verdict: simple (one api-dev agent, no contracts folder).

Every change is in exercise1/api, exercise1/api.Tests and one new exercise1/Directory.Build.props: three nullable annotations, two null checks that return a 404 result, a one-line pre-processor change, a parameterised person lookup in one handler, the props file, tests and a README changelog line. No schema or migration change and no UI change. Nothing can be split into independent parallel work.

The problem is real. A clean build of the baseline (dotnet build --no-incremental, SDK 10.0.402, observed) reports exactly the 6 warnings the task lists, 0 errors, all in StargateAPI.csproj. api.Tests has no warnings of its own and already sets TreatWarningsAsErrors in its own csproj. StargateAPI.csproj does not, so a plain dotnet build passes with warnings.

A prototype of this plan, built in a scratch copy, was checked against every acceptance criterion except the GET 404 (see 2.1). Results: 0 warnings, -warnaserror passes, all 61 existing tests pass, dotnet ef migrations has-pending-model-changes reports "No changes have been made to the model since the last migration", and a deliberate CS0168 fails a plain build. Nothing was left in the repo.

2. Wrong assumptions in the task (read first)

2.1 GET /AstronautDuty/{name} never runs the handler that has the bug

Controllers/AstronautDutyController.cs:24 sends GetPersonByName, not GetAstronautDutiesByName. Observed on the seeded Development database: GET /AstronautDuty/Nobody returns 200 {"person":null,"success":true,"message":"Successful","responseCode":200}, not a 500. The null dereference in GetAstronautDutiesByNameHandler (warnings 4 and 5) cannot be reached over HTTP today.

That means the acceptance criterion "GET /AstronautDuty/{name} with an unknown name returns 404" cannot be met unless the controller is rewired to the duties query. The task's own decisions put that out of scope ("the wrong query in the controller ... stay[s] in [its] own task"), and rewiring would also change the success response, which gains astronautDuties. Both choices are set out in Q1. This plan assumes option A: the handler returns the 404 and is tested at handler level, and the HTTP response for this route stays as it is today.

2.2 POST /AstronautDuty with an unknown person is a 400, not a NullReferenceException

CreateAstronautDutyPreProcessor (Business/Commands/CreateAstronautDuty.cs:33-35) looks the person up with EF and throws BadHttpRequestException("Bad Request"). Observed in Development: HTTP 400 whose body is the developer exception page (a text/plain stack trace with file paths, request headers and no BaseResponse). The handler's null dereference (:60, warning 6) is only reachable if the pre-processor is bypassed. The fix still has to change the pre-processor, because a pre-processor cannot return a response. Moving to 404 is the behaviour change the task authorises.

2.3 The obvious fix would make SQL injection worse

The handler reads the person again with interpolated SQL (:56-58: WHERE '{request.Name}' = Name). Today the pre-processor's parameterised EF lookup blocks every name that is not a real person, injection payloads included. If the pre-processor stopped rejecting unknown names and the handler kept its interpolated lookup, a name such as x' OR '1'='1 would match the first person in the table, and the request would write a duty to that person. The plan therefore swaps that single lookup for parameterised EF (decision D4). The other interpolated queries in the handler interpolate only the integer person.Id and stay exactly as they are.

4. Approach and decisions

D1. Navigation properties: Person?, not required (warnings 1, 2)

AstronautDetail.Person and AstronautDuty.Person become public virtual Person? Person { get; set; }. That is accurate: entities read with Dapper or AsNoTracking without Include really have a null navigation. Requiredness in EF comes from the non-nullable int PersonId foreign key, so the relationships stay required. Verified in the scratch copy: has-pending-model-changes reported no changes and the snapshot is unchanged.

Rejected: required Person Person. Every new AstronautDetail { ... } / new AstronautDuty { ... } would then have to set Person (CreateAstronautDuty.cs:66,100, DevelopmentSeedData, tests), or fail with CS9035. It would also claim a guarantee that Dapper reads do not keep.

D2. GetAstronautDutiesByNameResult.Person becomes PersonAstronaut? (warning 3)

This matches GetPersonByNameResult and the UI type person: PersonAstronaut | null. The JSON property name and type do not change, and a null is written as "person": null, as it is today.

D3. Unknown name in GetAstronautDutiesByNameHandler returns a 404 result (warnings 4, 5)

Straight after the first query (:30), add:

if (person is null)
{
    result.Success = false;
    result.Message = "Person not found";
    result.ResponseCode = (int)HttpStatusCode.NotFound;
    return result;
}

(This needs using System.Net;.) The 404 is produced in the handler, as data, not in the controller. That follows the existing BaseResponse/GetResponse pattern, so responseCode always equals the HTTP status and controllers stay thin. Body: {"person":null,"astronautDuties":[],"success":false,"message":"Person not found","responseCode":404}. The message is a fixed string and does not echo the name, so unbounded or hostile input is never reflected. The interpolated person query at :28 stays as it is (task 001 and the duties work own it). It is not reachable over HTTP today.

D4. Unknown person on add-duty: the handler returns a 404 result; the pre-processor lets the request through (warning 6)

  1. Pre-processor (CreateAstronautDuty.cs:35): replace if (person is null) throw new BadHttpRequestException("Bad Request"); with if (person is null) return Task.CompletedTask; and a one-line why-comment: the handler answers 404, and a pre-processor cannot return a response. Because the early return comes before the duplicate check, an unknown person always gets 404, even when another person already has a duty with the same title and start date. The duplicate check (:37-39) is unchanged for known people, so they still get a 400.
  2. Handler (:56-58): replace the interpolated Dapper lookup with 
    var person = await _context.People.AsNoTracking()
    .FirstOrDefaultAsync(z => z.Name == request.Name, cancellationToken);

if (person is null)
{
    return new CreateAstronautDutyResult
    {
        Success = false,
        Message = "Person not found",
        ResponseCode = (int)HttpStatusCode.NotFound
    };
}
    Then declare var query at the existing :60 line. Lines 60-116 are otherwise untouched: they interpolate only the integer person.Id, and duty rules 3-7 belong to the duties work. Body: {"id":null,"success":false,"message":"Person not found","responseCode":404}, which is the existing CreateAstronautDutyResult shape.

Why EF here: see 2.3. This is the only way to stop rejecting unknown names in the pre-processor without opening an injection path. The comparison is the same as the pre-processor's (Name = @p, SQLite BINARY collation) and the same as the old 'x' = Name, so every request that succeeds today finds the same person. Side effect: a real person whose name contains ' (for example O'Brien) passes the pre-processor today but then breaks the handler's SQL. After this change their duty can be added. That request fails today, so the "unchanged for succeeding requests" criterion still holds. This does not fix SQL injection in general: the GET handlers and GetPersonByName stay as they are.

Rejected: throw BadHttpRequestException(..., 404) from the pre-processor. The status code would be right, but the body would be a stack trace (Development) or empty (Production), with no responseCode. That breaks the BaseResponse rule.
Rejected: keep the pre-processor's 400 and add only a handler null check. That fixes the warning, but HTTP would still answer 400, failing the 404 acceptance criterion.
Rejected: drop the pre-processor lookup entirely. The duplicate check would then run first, and an unknown person with a colliding duty would get 400 instead of 404.

D5. exercise1/Directory.Build.props

<Project>
  <!-- Every .NET project under exercise1/ fails the build on any warning (CLAUDE.md: warnings as errors). -->
  <PropertyGroup>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <!-- NuGet audit results come from an external feed that changes without a commit (NU1900 = feed unreachable,
         NU1901-NU1904 = low..critical advisory). They are still reported as warnings, but must not break every
         branch the day an advisory is published or the feed is offline. Gate them in CI instead. -->
    <WarningsNotAsErrors>$(WarningsNotAsErrors);NU1900;NU1901;NU1902;NU1903;NU1904</WarningsNotAsErrors>
  </PropertyGroup>
</Project>
  • Scope: MSBuild picks up the nearest Directory.Build.props above each project, and none exists in the repo today, so both api and api.Tests inherit it, as will any future project. exercise1/ui is not an MSBuild project and is unaffected. Verified: dotnet msbuild -getProperty:TreatWarningsAsErrors returns true for both projects.
  • Test csproj: remove the now-redundant <TreatWarningsAsErrors>true</TreatWarningsAsErrors> from StargateAPI.Tests.csproj:8 so the setting lives in one place.
  • -warnaserror on the command line: the SDK copies WarningsNotAsErrors into MSBuildWarningsNotAsErrors (verified with -getProperty), so the CLAUDE.md command dotnet build -warnaserror follows the same exception list. A live advisory has not yet been seen to stay a warning, see 11.
  • Why this is not a suppression: no compiler warning is exempt, nothing is hidden (NoWarn is untouched), and audit findings still print. Only external, time-varying supply-chain data is kept from failing the compile. Rejected: leave NU190x as errors. A newly published advisory, or the sandbox firewall blocking the audit feed (NU1900), would break every build and every branch, including unrelated fixes, with no change in the repo.
  • dotnet ef / design-time: dotnet ef builds the project first, so a warning now blocks migrations add and database update. That is intended. EF-scaffolded migrations compile cleanly (both existing ones do, and they carry #nullable disable). IDE design-time builds will show warnings as errors too.
  • SDK roll-forward: global.json pins 10.0.100 with rollForward: latestFeature, and the sandbox uses 10.0.402. A newer SDK that adds analyzer warnings will break the build until they are fixed. That is the policy working as intended, not a reason to suppress anything. This is noted in the README.

7. Domain rules

  • Rule 1 (person identified by name): the new EF lookup uses the same exact, case-sensitive equality as before, so the same person is matched.
  • Rule 2 (no assignment means no detail or duty rows): an unknown or hostile name on POST writes nothing. Tests T5-T7 compare the database dump before and after.
  • Rules 3-7 (duty rules): the logic is not touched (CreateAstronautDuty.cs:60-116 unchanged apart from the var declaration). Their known defects remain with the duties work.

8. Tests (api.Tests, existing infrastructure)

All tests use a TestDatabase per test (TestDatabase.cs): Migrate(), seed through CreateContext(), then run. The handlers take a StargateContext, and Dapper opens the EF connection itself, so handler tests need no mocks. POST tests run through MediatR so the pre-processor is included. They build a ServiceCollection with AddDbContext<StargateContext>(o => o.UseSqlite(db.ConnectionString)) and AddMediatR configured as in Program.cs:19-23 (assembly from typeof(CreateAstronautDutyHandler).Assembly, because the top-level Program is not public). The duplicated registration is a known drift risk; full WebApplicationFactory tests would need Microsoft.AspNetCore.Mvc.Testing, a new package, and are deliberately not added here.

10. Risks and rollout

  • Data: none. No migration, the model is unchanged (verified), and no existing row is touched.
  • Backward compatibility: the only observable change is POST unknown person 400 → 404 (section 6), plus an O'Brien-style name now succeeding where it returned 500 before.
  • Other branches: once merged, branches for 001, 002 and 006 that add warnings will fail to build. That is intended, and the task says they must fix, not suppress. Merge this before them, as the task notes recommend. Expect merge conflicts in CreateAstronautDuty.cs / GetAstronautDutiesByName.cs with the duties work.
  • Supply chain: NU190x stay warnings (D5). Until CI exists, a new advisory shows up only as a build warning. Recommended follow-up: a CI step running dotnet list package --vulnerable --include-transitive that fails on high or critical.
  • Rollback: revert the single commit. Nothing persists outside the code.

12. Questions for the user

Q1. GET /AstronautDuty/{name} 404 (blocks the acceptance criterion as written). The route runs GetPersonByName (2.1), so an unknown name returns 200 today and fixing the handler alone does not change that.

  • A (recommended, planned): fix and test the handler (404 result), leave the controller as is, and change the acceptance criterion to "the GetAstronautDutiesByName handler returns 404 for an unknown name; the HTTP 404 for this route arrives with the controller rewire in the duties task." This keeps your binding decisions intact: no response-shape change, and the controller query stays out of scope.
  • B: also rewire AstronautDutyController.cs:24 to send GetAstronautDutiesByName. Unknown names then return 404 over HTTP, but successful responses gain astronautDuties (an additive shape change, already expected by ui/src/app/api/models.ts:34-37). The interpolated name query in that handler would then be exposed instead of the identical one in GetPersonByName, which is no worse. This plan would need a contracts note, more tests, and to drop the "shape unchanged" acceptance criterion for this route.

Q2. NuGet audit severity. The plan keeps NU1900-NU1904 as warnings (D5). Recommendation: accept. The alternative is to keep NU1903/NU1904 (high and critical) as errors. That is safer for supply chain, but any newly published advisory would break every branch's build overnight.
