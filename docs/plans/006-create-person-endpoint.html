4. Approach

4.1 C1: the ASCII-only name rule (one definition, all four endpoints)

Normalize(value) = value.Trim(' ', '\t', '\n', '\v', '\f', '\r')      // ASCII whitespace only
IsValidName(n)   = 1 <= n.Length <= 100 && Regex.IsMatch(n, @"^(?=[ .'-]*[A-Za-z0-9])[A-Za-z0-9 .'-]+\z")   // CultureInvariant, no IgnoreCase, 100 ms timeout
  • Trim set: ASCII whitespace only. Non-ASCII whitespace at an edge (NBSP, U+3000, U+0085, U+2003, ...) is not trimmed, so the name is 400.
    • Why: one rule with no exceptions. "Every character outside the ASCII set is rejected wherever it is" is deterministic and easy to state, test and explain.
    • Silently trimming 19 non-ASCII characters while rejecting all the others would be the one hidden exception. Under "assume normal English characters", an NBSP is a paste artefact the caller should see.
    • ASCII tab, CR and LF at the edges are still trimmed, which keeps today's write behaviour. Existing tests H3/H9 ("Mira Okafor\t") and R11 ("\r\nAda\r\n") stay as they are.
  • Pattern written out as A-Za-z0-9, never \d (it matches Arabic-Indic and other digits) and never with RegexOptions.IgnoreCase (under it K U+212A KELVIN SIGN matches k, and ſ matches s). \z stays, so a trailing \n never matches. Tests R4b and R25 pin these.
  • At least one ASCII letter or digit (rev. 3). Punctuation-only values (., .., ', -, . -, 100 periods) are invalid; a., A-1, . a and 7 are valid. Enforced by the lookahead (?=[ .'-]*[A-Za-z0-9]): it can only consume allowed punctuation before it needs a letter or digit, so it fails fast on other characters and is linear (R28 bounds the time). Reason: .. as a path segment is resolved away by URL normalisation, so the UI's getPerson would call /api/. Tests R27, R28, create P19, F6, F7.
  • Length is measured after trimming, 1-100, as the task's own rule says. A 100-letter name padded with spaces stays valid (R18).
  • Raw bound (800): removed. It existed only so NFC never ran on unbounded input. ASCII trimming and the length check are linear and cheap, and the regex runs only on at most 100 characters.
  • [RequestSizeLimit(4096)]: kept on PUT and POST.
    • It bounds the body before JSON binding allocates anything.
    • It is already shipped and tested for PUT (413), and keeping it makes POST consistent.
    • 4096 bytes is far above any valid body: a 100-character name in JSON is at most about 210 bytes even with every ' escaped as '.
    Query and route values on GET are bounded by Kestrel's request-line limit (8 KB) and then by the 100-character check.
  • Message becomes "Use only English letters (A-Z), digits, spaces, hyphens, apostrophes and periods, with at least one letter or digit (at most 100 characters)." (rev. 3 wording) The old "letters" would mislead someone who typed Zoë. Clients must not parse messages, so this is not breaking. R19 is updated.
  • Case-insensitivity: SQLite NOCASE folds ASCII only, which now covers every valid name exactly. The "Émile vs émile" limit disappears because both are 400.
  • Read side: the GET attributes keep validating the raw value with the same pattern constant. So a GET value with a tab or newline at an edge is 400 (as today, H2b), while a write trims it.
    • This inconsistency is pre-existing and unchanged.
    • Task 008's single query object is the place to unify it (section 10).
    • A whitespace-only GET value still means "no filter".
  • Code: InputRules.cs (rewrite), ValidNameAttribute.cs (drop the raw bound), UpdatePerson.cs:56 (drop the raw bound), and the PUT EndpointDescription ("NFC-normalised" becomes "trimmed"). GetPeople and GetPersonByName keep calling InputRules.Normalize; the name stays and only its meaning changes. Exact code: data.md.

  • GetPeople.cs SQL: (@Name IS NULL OR a.Name = @Name COLLATE NOCASE). The parameter is Name = Normalize(request.Name).
    • Delete NamePattern, EscapeLike and the ESCAPE clause.
    • The comparison can use IX_Person_Name.

4.3 C3: POST /Person

Unchanged from revision 1 except for the rule. Steps:

  1. CreatePersonRequest { [Required, ValidName] string? Name }.
  2. Handler: Normalize, then IsValidName, throwing ArgumentException if it fails.
  3. Pre-check with NOCASE AnyAsync: a match is 409.
  4. Add, then SaveChangesAsync(ct). A unique violation (IsUniqueViolation) is 409.
  5. On success, 201 with Id, plus a [JsonIgnore] Name for the controller.

The controller:

  • Attributes: [Consumes("application/json")], [RequestSizeLimit(4096)] and the Swagger attributes.
  • No try/catch.
  • Created("/Person?name=" + Uri.EscapeDataString(storedName), result) on 201, otherwise GetResponse.

Malformed JSON (rev. 3). Program.cs adds .AddJsonOptions(o => o.AllowInputFormatterExceptionMessages = false). For POST and PUT, a body System.Text.Json cannot read as the request type is still 400 ValidationProblemDetails with non-empty errors, but every message is generic (for example {"$":["The input was not valid."],"request":["The request field is required."]} for [], or an entry under $.name for {"name":4242}). Tests M1 in both HTTP files assert that no key or message contains StargateAPI, System., Path, LineNumber, BytePosition or converted.

The order of checks is 415/413, then 400, then 409. CreatePersonPreProcessor is deleted: a pre-processor can only throw, the race has to be caught in the handler anyway, and PUT already uses handler checks. A 409 returns id: null.

4.4 Location

The header is /Person?name=<Uri.EscapeDataString(stored name)>, for example O'Brien Jr. becomes /Person?name=O%27Brien%20Jr.. After C2, a GET of it returns exactly the created person, and after 008 it still does. The value is relative and always ASCII.

4.5 Main alternative rejected

  • Trim all of string.Trim()'s set, so that NBSP at an edge is trimmed and accepted. Rejected for the reason in 4.1: it would be the only place a non-ASCII character is accepted.
  • A raw 100-character limit (before trimming). Rejected because it breaks the task's "1 to 100 after trimming" rule and today's padded-name behaviour (R18), and because the raw bound has no remaining purpose.
  • Rejected in revision 1 and still rejected: accepting both body shapes, and using 422.

9. Risks and rollout

  • Breaking changes:
    • Non-ASCII input is 400 everywhere.
    • The name filter is exact, so partial-name searches now return nothing.
    • POST has a new body shape and returns 201 and 409.
    All are accepted by the user and listed in the README changelog. No UI component uses the name filter today (grep).
  • Existing non-ASCII rows (from POST before 006 or PUT since 002) stay in the database.
    • They are still listed by GET /Person and can be renamed by id via PUT to an ASCII name.
    • They can no longer be found by name: ?name= or /Person/{name} with that value returns 400.
    • Renaming to the same non-ASCII name returns 400.
    • There is no data migration. The seed data is ASCII. See Question 1.
  • Legacy NFD rows: covered by the point above. The revision 1 risk is moot.
  • The migration comment "which is what the app trims" is now inaccurate. The migration may not be edited; the README note explains it.
  • Rollback: revert the merge commit (or C3 alone, or C2 alone; they are separate commit sets). There is no schema or data to undo. Names created under the ASCII rule are valid under the old rule too.
  • Unverified, each with a cheap check:
    1. Swashbuckle omits the [JsonIgnore] Name from the CreatePersonResult schema. Check: P12. Fallback: build Location from InputRules.Normalize(request.Name) in the controller.
    2. POST with no body and no Content-Type returns 415. Check: P7c (proven for PUT).
    3. 413 for POST on Kestrel. Check: K3 and QA 6.
    4. Swashbuckle emits the new GET pattern string verbatim. Check: F4 asserts that it equals the literal pattern (rev. 3: the new pattern). Today's H9 checks only that it is present.
    5. Revision 1's "non-ASCII Location" risk is no longer reachable (all non-ASCII is 400), but K1 still checks the exact header on Kestrel.

Open: not part of this task, not fixed (recorded in revision 3; the user has not yet decided whether the fix goes into this PR or a separate security task, Question 2)

  1. Second-order SQL injection through POST /AstronautDuty. Business/Commands/CreateAstronautDuty.cs:56 builds SELECT * FROM [Person] WHERE '{request.Name}' = Name by string interpolation; lines 70 and 100 interpolate person.Id the same way. The registered CreateAstronautDutyPreProcessor first requires a person whose name equals request.Name (EF, parameterised), so an attacker stores the payload as a person name first. The name rule allows apostrophes and spaces, and POST /Person has no authentication, so a name such as a' OR Id IS 3 OR 'a is valid; POST /AstronautDuty with that name then evaluates 'a' OR Id IS 3 OR 'a' = Name, loads person 3, and writes a new duty and the current rank and title to person 3. This predates task 006 (before it, POST /Person stored any string); 006 narrows the payload alphabet but does not close the hole. Deferred fix: parameterise the three queries at CreateAstronautDuty.cs:56, :70 and :100 (Dapper parameters), with an HTTP test that stores the payload name and checks no other person changes.
  2. Same pattern, not reachable today: Business/Queries/GetAstronautDutiesByName.cs:28 (and :38). AstronautDutyController.GetAstronautDutiesByName currently sends GetPersonByName, so this handler is not called over HTTP; it becomes exploitable when it is wired up. Parameterise it in the same fix.
  3. No authentication on any write endpoint (POST /Person, PUT /Person/{personId}, POST /AstronautDuty). Program.cs calls UseAuthorization but configures no scheme or policy. Unchanged by this task; any caller can create and rename people.
