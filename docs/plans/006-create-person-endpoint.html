Plan 006: Make POST /Person a proper, validated create endpoint

1. Summary and verdict

POST /Person will take a JSON object { "name": "..." }. On success it returns 201 Created with { id, success, message, responseCode } and a Location header. Validation reuses the shared name rule from task 002 unchanged: the same [ValidName] attribute, and the same InputRules.Normalize (NFC, then trim) in the handler. Invalid input returns 400. A duplicate returns 409, whether a pre-check in the handler catches it or the unique index (SqliteErrors.IsUniqueViolation) does. The pipeline gives 415 and 413 exactly as it does for PUT. The controller try/catch that returns ex.Message is removed, and the dead CreatePersonPreProcessor is deleted. The UI client gets StargateApi.createPerson(name), which emits typed outcomes. There is no schema change.

Verdict: multi (api + ui, joined by an HTTP contract; same shape as 002). The UI part is one client method, three types and Vitest tests. It depends only on the wire contract, so ui-dev can build it in parallel against docs/contracts/006/ without waiting for the API. There is no db subtask: the unique index and the name rule already exist on main.

The problem is real. I checked every bullet in the task against main and all of them hold. Two details in the task need correcting:

  • The acceptance criterion says the new person appears with "null rank, duty title". On the wire, currentRank and currentDutyTitle are empty strings for an unassigned person (PersonAstronaut.cs defaults them to string.Empty; contract 002 and test P1 pin ""). Only careerStartDate and careerEndDate are null. The tests assert that real shape.
  • "Missing body returns 400" applies only when the request still says it is JSON. A request with no Content-Type at all is rejected by [Consumes] with 415 before binding runs, the same as PUT (contract 002, Amendment 1). See 4.3.

3. Probe run (1 of 3; scratch only, removed afterwards)

Kestrel and a non-ASCII Location. I wrote a scratch minimal app on the .NET 10 SDK and served it with real Kestrel:

  • Setting Location: /Person?name=Zoë returned HTTP 500 and logged InvalidOperationException: Invalid non-ASCII or control character in header: 0x00EB.
  • Uri.EscapeDataString("O'Brien Zoë Jr.-x") produced O%27Brien%20Zo%C3%AB%20Jr.-x, which Kestrel sent with 201.

Why this matters: the header is written after the handler has committed the row. An unescaped Location would therefore store the person and then answer 500, and a retry would get 409. The in-memory TestServer does not validate header characters, so only a Kestrel-hosted test (pattern: PersonHttpProductionTests, factory.UseKestrel(0)) or QA can catch it. Escaping is mandatory and is tested on Kestrel (K1).

Facts taken from merged tests rather than probes:

  • A bare JSON string sent with application/json to an object-typed [FromBody] returns 400 without echoing the value (PersonUpdateHttpTests.P7, "\"Tokenabc\""). With text/plain it returns 415 (P9).
  • An empty body with a JSON content type returns 400 (P7, "").
  • Production 500s have an empty body when served by Kestrel (PersonHttpProductionTests).

4. Approach

4.1 Request, handler, result (Business/Commands/CreatePerson.cs)

  • New CreatePersonRequest (the HTTP body): [Required, ValidName] public string? Name { get; init; }. This is the same attribute as UpdatePersonRequest, so the rule is not duplicated. Unknown properties are ignored.
  • CreatePerson (the MediatR request) keeps required string Name, carrying the raw value. The handler normalises it, exactly like UpdatePerson.
  • Handler order, mirroring UpdatePersonHandler:
    1. Raw length above InputRules.MaxRawLength makes the name empty. Otherwise InputRules.Normalize.
    2. If !IsValidName, throw ArgumentException("Invalid name."). This is unreachable over HTTP and never includes the value.
    3. Pre-check AnyAsync(p => EF.Functions.Collate(p.Name, "NOCASE") == name). If a match exists, return 409.
    4. People.Add, then SaveChangesAsync(ct). Catch DbUpdateException when SqliteErrors.IsUniqueViolation and return 409. Any other exception propagates.
    5. Log Created person {PersonId}. Return 201.
    The CancellationToken flows through every call.
  • CreatePersonResult:
    • int? Id: set on 201, null on 409. The field name stays id, as the task decided.
    • [JsonIgnore] string? Name: the stored name, used only by the controller to build Location. It is never serialised.
    • 201 sets message "Successful". 409 sets success false and message "A person with this name already exists", the same text as PUT.
  • Delete CreatePersonPreProcessor (see 4.4).

4.2 Controller action

  • Attributes: [HttpPost("")], [Consumes("application/json")] and [RequestSizeLimit(4096)].
  • Swagger metadata: [EndpointSummary("Create a person")] and [EndpointDescription(...)].
  • [ProducesResponseType] entries: 201 CreatePersonResult, 400 ValidationProblemDetails, 409 CreatePersonResult, 415 ProblemDetails, and 500 with no type.
  • Signature: CreatePerson([FromBody] CreatePersonRequest request, CancellationToken cancellationToken). It sends new CreatePerson { Name = request.Name ?? string.Empty }.
  • On a 201 result it returns Created(location, result). Otherwise it returns this.GetResponse(result).
  • No try/catch. Location is built by one private static helper: "/Person?name=" + Uri.EscapeDataString(storedName) (see 4.5).

The status always matches responseCode. Created() writes 201 and the handler sets ResponseCode = 201.

4.4 One duplicate-check mechanism: delete the pre-processor

Decision: delete CreatePersonPreProcessor and keep the check in the handler, as PUT does. Registering the pre-processor instead was rejected for three reasons:

  1. A MediatR pre-processor cannot return a result. It can only throw. Turning that throw into 409 would need an exception-to-status mapping (a global exception handler), which this task explicitly leaves out of scope.
  2. The race path (unique index violation at SaveChanges) has to be caught in the handler anyway. A pre-processor would split one rule across two places.
  3. PUT already uses handler-level checks (UpdatePerson.cs). Two mechanisms for the same rule in the same controller would diverge.

When a global exception handler and a validation pipeline behaviour arrive (CLAUDE.md standard), both handlers can move together. That is a separate refactor. Program.cs needs no change; the MediatR.Pipeline using in CreatePerson.cs goes with the class. note CLAUDE.md's layout line still says "pre-processors (CreatePerson)". Agents may not edit CLAUDE.md, so I leave that for the user.

4.5 The Location header: recommend /Person?name=<encoded> (changes a task decision; see Question 1)

The task decided Location: /Person/{name}. Task 008 (ready, depends on 001 and 007) deletes GET /Person/{name}, and after that the route returns a plain routing 404. A Location built now would then point at nothing. The 008 developers might not notice, because nothing reads Location in the repo.

OptionToday (before 008)After 008Trade-off
/Person?name=<EscapeDataString(stored)> (recommended)200 GetPeopleResult. Contains match, so it lists the new person plus anyone whose name contains it (for example Ada also lists Adam Ray). The stored name always passes the read-side rule, so it is never a 400.200 with exactly that person (exact, case-insensitive, trimmed).Never dangles. It identifies a filtered collection rather than a single-resource URI, which is weaker REST semantics, but it is the only by-name lookup that survives 008. No change is needed in 008.
/Person/{EscapeDataString(stored)} (task decision)200 GetPersonByNameResult for exactly that person.404 (route removed).Accurate single-resource URI today. Dangles after 008, unless 008 also changes the header (a cross-task edit that is easy to forget).

Call: /Person?name=. The contract is written that way. If the user keeps the original decision, only the prefix in one helper and the expected header in tests P1-P3 and K1 change. The UI never reads Location, so ui-dev is unaffected either way.

  • The value is relative (RFC 9110 allows that). Resolved against the API base, it gives /api/Person?... behind the dev proxy.
  • Encoding uses Uri.EscapeDataString: RFC 3986 unreserved characters stay, everything else is percent-encoded as UTF-8. Space becomes %20, apostrophe %27, ë %C3%AB, and the result is ASCII only.
  • The stored (normalised) name is what gets encoded, never the raw input.

4.7 Main alternative rejected

Accept both body shapes (bare string and object) for one release. Rejected because the task decided a clean break, nothing in the repo calls the bare-string form, and a dual-shape binder needs a custom input formatter or JsonElement parsing, which would bypass the shared [ValidName] model validation. A second alternative, a 422 for rule violations, is not used: PUT uses 400 and 409, and CLAUDE.md lists 422 only as optional.

7. Domain rules

  • Rule 1 (a Person is uniquely identified by Name).
    • In code: Normalize (NFC and trim) runs before the comparison and before storage. A NOCASE pre-check gives a fast 409.
    • In the database: the existing unique index IX_Person_Name on the COLLATE NOCASE column is the guarantee. When a concurrent insert loses, it surfaces as IsUniqueViolation and maps to 409, never 500 and never two rows.
    • Known limits, unchanged from 002: case folding is ASCII-only, and compatibility characters and look-alikes are not unified (Question 2).
  • Rule 2 (no assignment means no astronaut rows). The handler adds only a Person and never touches AstronautDetail or AstronautDuty. Tests compare dumps of both tables before and after (H9, P14). The new person is then listed by GET /Person with "" rank and title and null dates.
  • Rules 3-7 are not touched.

9. Risks and rollout

  • Breaking for external callers: body shape, 200 to 201, and 409. Accepted by the user. Called out in the README changelog.
  • Non-ASCII Location: covered by escaping and the Kestrel test. A regression would mean a stored row behind a 500.
  • Legacy NFD rows: the 002 migration did not NFC-normalise existing names. A database that already holds an NFD name will accept its NFC twin. Seeded and new databases are not affected, and rows written since 002 are NFC. Accepted in 002; no new action.
  • Compatibility characters and look-alikes (Ａｄａ, ligatures, Cyrillic а): they pass the rule and are distinct names. That was already true for rename; create now makes it reachable by a new route. Question 2.
  • Development 500 page: the developer exception page shows the stack in Development only, as accepted in 001 and 002. Question 3 covers the acceptance criterion's wording.
  • Data impact: none. No migration, no change to existing rows.
  • Rollback: revert the merge commit. No data or schema to undo. People created in the meantime stay valid under the old code.
  • Unverified, with a cheap check:
    1. Swashbuckle 10 omits the [JsonIgnore] Name from the CreatePersonResult schema. Check: test P12 asserts the schema has no name property. If it appears, use [property: JsonIgnore] plus [SwaggerIgnore], or build Location in the controller from InputRules.Normalize(request.Name). That is a deterministic re-computation, not a second rule.
    2. In P7, a POST with no body and no Content-Type returns ProblemDetails 415 (proven for PUT in contract 002 Amendment 1). Check: HTTP test P7c.
    3. The 413 on Kestrel for POST. Check: K3 and QA item 6.

13. Questions for the user

  1. Location header target. The task decided /Person/{name}, but task 008 removes that route.
    • Recommendation: /Person?name=<encoded stored name>. It works today (contains match, so it may list extra people) and after 008 (exact). The contract is written this way.
    • Alternative: keep /Person/{name} and add "rewrite the Location" to task 008.
  2. Compatibility characters and look-alikes (recorded in the 002 notes and the PR #5 description). Today these all pass the shared rule and count as names distinct from their ASCII forms: fullwidth Ａｄａ, ligatures such as ﬁ, and cross-script look-alikes such as Cyrillic Аda. The reasons: NFC rather than NFKC, and ASCII-only case folding. 006 does not change this.
    • Recommendation: accept for 006. Then decide separately between:
      • (a) a hardening task that adds a persisted comparison key column: NFKC plus full Unicode case fold, with the unique index moved to it. This is robust and keeps the display name as typed.
      • (b) NFKC on the stored name itself. Simpler, but it rewrites what users typed (ﬁ becomes fi).
      Cross-script look-alikes need UTS #39 confusable skeletons and are probably not worth it for an internal system of record. I suggest accepting that permanently.
  3. "Unexpected failures return a generic 500 message." As in 001 and 002, this plan removes the try/catch, so a Production 500 has an empty body (logged by the host), and Development shows the developer exception page. The criterion is met in the sense that nothing internal leaks, but no message is shown. A global ProblemDetails exception handler would add a generic message for every endpoint, but the task puts it out of scope.
    • Recommendation: accept the empty-body 500 here, and add the global handler as its own small task.
