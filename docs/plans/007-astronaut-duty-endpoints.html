1. Summary and verdict

The problem is real, and I confirmed it on main. Both duty handlers build SQL by string interpolation of the person's name. QA for task 006 replayed the attack (docs/qa/006-create-person-endpoint.html, observation 1). A person named a' OR Id IS 3 OR 'a was created through the unauthenticated POST /Person, then a duty was posted for that name, and the duty was written to Tomas Lindqvist (PersonId 3). The attack closed his Pilot duty and overwrote his AstronautDetail. A real name such as Aoife O'Brien Jr. got a 500 whose body contained the SQLite syntax error and a stack trace.

The task's premises are all correct against 280fcd9, with one detail to add. Leaving out dutyStartDate does more than store 0001-01-01. For a person who already has a duty, the handler computes DateTime.MinValue.AddDays(-1), which throws ArgumentOutOfRangeException, and the caller gets a 500 (I verified this in a scratch probe). That is one more reason for the date bounds in section 4.4.

Verdict: multi (api + ui). The task changes a response contract the UI consumes: the GET route moves to a query parameter, the 404 is new, and the duty item shape is fixed. CLAUDE.md requires the UI client to change in the same commit. The UI work is small, but it is independent once the contract is fixed. This is the same split as tasks 002 and 006. The API part is one subtask: the security fix and the POST hardening rewrite the same file, so splitting it would only create merge conflicts.

3. Approach

3.1 Security fix (first, non-negotiable)

  1. Delete CreateAstronautDutyPreProcessor and its registration in Program.cs, as task 006 did for people. The handler resolves the person exactly once with one parameterised EF LINQ query. It trims the name (InputRules.Normalize), matches case-insensitively and exactly (EF.Functions.Collate(p.Name, "NOCASE") == name), orders an exact-case match first and then by Id, and takes the first row (Amendment 1: the same order as GetPersonByName and the GET handler; data.md section 1a). Every later read and write uses that person's Id and nothing else. The response's Location header uses that person's stored Name.
  2. The create handler uses EF LINQ only, with no Dapper in the write path. It loads the detail and the latest duty as tracked entities and changes them in place, then calls one SaveChangesAsync(ct). This replaces the Dapper-read-then-Update() pattern, so every value reaches SQLite as a parameter.
  3. The GET handler keeps Dapper (the project convention for reads). It uses two static const string raw literals with @Name and @PersonId parameters through CommandDefinition with the token, the same pattern as GetPersonByName and UpdatePerson.ReadBackSql. The exact SQL is in data.md section 2.
  4. The duty-loading query is parameterised: SELECT Id, PersonId, Rank, DutyTitle, DutyStartDate, DutyEndDate FROM [AstronautDuty] WHERE PersonId = @PersonId ORDER BY DutyStartDate DESC, Id DESC. It maps to a new DTO, AstronautDutyItem.
  5. Neither handler, nor anything they call, contains a $-string, concatenation, FromSqlRaw or ExecuteSqlRaw. Values only ever travel as parameters.

Source-level guard test: no. The test reviewers removed source scans in task 006 (GetPeopleQueryTests.F5, R25's text checks) because they break on harmless refactors and pass on real regressions written differently (for example string.Format, + or a helper method). The guard here is behavioural:

  • The hostile HTTP matrix proves the outcome: other people's rows stay byte-identical.
  • For the create path, which is EF-only by design, a handler test attaches the existing CountingCommandInterceptor. It asserts that no executed CommandText contains the hostile marker text, so values arrived as parameters. That test fails if someone reintroduces FromSqlRaw/FromSqlInterpolated with concatenation or a raw command through EF.
  • Its limit, stated honestly: Dapper calls on _context.Connection do not pass through EF interceptors. For the GET path the behavioural read-path tests are the guard. The $"SELECT/$"""/FromSqlRaw grep from the acceptance criteria is a security-reviewer and QA checklist item, not a unit test.

3.2 GET /AstronautDuty?name=

  • [HttpGet("")] with [FromQuery, Required, ValidName, Description(...)] string? name and CancellationToken. The action sends GetAstronautDutiesByName and returns this.GetResponse(result). There is no try/catch, and the controller no longer references GetPersonByName (task 008 depends on this).
  • A missing, empty or whitespace-only name (spaces, tab, newline) is 400 with only the Required message (Amendment 1: the query binder turns a whitespace-only value into null, so the name rule never sees it; the plan said "Required plus the name rule"). Over 100 characters, a disallowed character, or no letter or digit is 400 (the rule). The body is a ValidationProblemDetails under key name and never echoes the input.
  • A repeated parameter (?name=a&name=b) binds the first value (Amendment 1, test G7c). This is safe: exactly one person resolves and the values are never combined.
  • Status codes: 200 with person plus astronautDuties, newest first (empty for a person with no assignment, rule 2). An unknown name is 404 with {person:null, astronautDuties:[], success:false, message:"Person not found", responseCode:404}.
  • Exact response DTO: duty items become the new Business/Dtos/AstronautDutyItem with {id, personId, rank, dutyTitle, dutyStartDate, dutyEndDate}. The "person": null member disappears. This is not a break for any consumer, because the old route never returned duties, and the UI's AstronautDuty interface already has exactly these six fields. Returning a DTO instead of the EF entity keeps the wire shape independent of the entity's navigation properties.
  • GET /AstronautDuty/{name} is removed. No action matches any more, so routing answers 404 with an empty body. A test pins this.

3.3 POST /AstronautDuty

  • There is a new body type, CreateAstronautDutyRequest, with nullable properties, like CreatePersonRequest:
    • name, rank and dutyTitle are [Required, ValidName] (the shared ASCII rule; RETIRED, Mission Specialist and 2LT all pass).
    • dutyStartDate is a DateTime? with [Required, ValidDutyDate].
    The MediatR command stops being the body. It keeps raw values, and the handler normalises them.
  • [Consumes("application/json")], [RequestSizeLimit(4096)], EndpointSummary/EndpointDescription, and ProducesResponseType for 201, 400, 404, 409, 415 and 500.
  • Order of checks: 415 and 413, then 400 (body and rules), then 404 (unknown person), then 409.
  • Success is 201 with body {id, success:true, message:"Successful", responseCode:201} and Location: /AstronautDuty?name=<Uri.EscapeDataString(stored person name)>. The stored name, not the request's casing or padding, matches the PersonController.PersonLocation pattern.
  • Unknown person: 404 {id:null, success:false, message:"Person not found", responseCode:404}. Nothing is written.
  • Duplicate: 409 {id:null, success:false, message:"A duty with this title and start date already exists for this person", responseCode:409}. Nothing is written. "Duplicate" means the same person, the same title compared case-insensitively (ASCII NOCASE, as titles are matched everywhere else in the API) and the same start date (date part only, on both sides). The same title and date for another person is allowed.
  • Database unique-constraint mapping: only what exists. No index on AstronautDuty enforces the duplicate rule; task 009 owns that index. The only unique index this write can hit is IX_AstronautDetail_PersonId, when two concurrent first duties for one person race. The handler maps that SqliteErrors.IsUniqueViolation to 409 with the fixed message "The person's duties were changed by another request". Today that race is a 500. No other index is added or mapped.
  • No exception text in any response. The global exception handler is a separate follow-up.

3.4 Rules 3-7: behaviour preserved, two inseparable normalisations called out

The rules block is translated line for line from Dapper to EF. For the same valid inputs the persisted rows are identical to today's:

  • A first duty creates the detail with CareerStartDate = start.
  • Later duties update rank and title.
  • A RETIRED title sets CareerEndDate: to the start date on a first duty (the defect stays), and to start minus 1 on later duties.
  • The latest duty by start date is closed at start minus 1.
  • The new duty is open.

Two changes cannot be separated from the fix, so I call them out:

  1. Rank and title are trimmed before storage, with the same ASCII trim as names. The validation rule is defined on the trimmed value, so storing the untrimmed value would store something the rule never checked. The only observable difference is padded input: " RETIRED " now counts as retired (exact-case RETIRED only; case-folding stays in task 009).
  2. Tie-break Id DESC when two duties of one person share the latest start date. Today SQLite picks either row (undefined). Ties can exist only with different titles on the same day, which task 009 will reject. The tie-break makes "which duty is closed" deterministic and testable.

Transaction: no, not in this task. The single SaveChangesAsync already writes all rows atomically, which satisfies "multi-row writes in one transaction". Wrapping the reads in a transaction would not stop the race on SQLite: a deferred transaction takes no lock until the first write, and two writers then deadlock on the lock upgrade, so the loser gets SQLITE_BUSY and a 500, which is worse than today. The real fix needs BEGIN IMMEDIATE, busy handling, 409 mapping and the partial unique index together, which is the design task 009 already owns (its decision 5, open questions 5 and 10).

3.5 Main alternative rejected

Keep the pre-processor and only parameterise the handler's SQL. That is the smallest diff that stops this particular payload, but it keeps two lookups, with different code and potentially different matching rules (the pre-processor is EF ==, the handler would be Dapper), that decide "which person" separately. That is the root cause the task names. It also keeps BadHttpRequestException, which cannot produce 404 or 409. Rejected.

Second alternative rejected: a personId in the POST body instead of the name. Decision 6 rules it out, and it would not fix the GET.

6. Domain rules

RuleHow it stays true
1. A person is identified by nameBoth handlers resolve the person once, with an exact, trimmed, ASCII case-insensitive match. On a migrated database the unique NOCASE index IX_Person_Name guarantees at most one row. On a database that predates it, all three name lookups pick the same person: exact-case match first, then the lowest Id (Amendment 1). A fragment such as ra never matches. An injection payload is a literal name, so it matches only the person with exactly that name.
2. No assignment means no astronaut rowsGET returns an empty astronautDuties list. Any rejected POST (400, 404 or 409) writes nothing, which tests assert with a full-table dump comparison.
3-7Behaviour unchanged for valid, unpadded input (section 3.4). A regression test pins the normal "second duty arrives" case and two neighbours. Defects deliberately left for task 009: a first RETIRED duty gets CareerEndDate = start instead of start minus 1; RETIRED is matched case-sensitively; back-dated and same-day duties are accepted, and the latest duty is closed even when it already has an end date; there is no transaction around read-decide-write; there is no unique index for the open duty or for (PersonId, DutyStartDate); a later non-retired duty does not clear CareerEndDate; a numeric offset in dutyStartDate is converted to server local time before .Date (section 9).

9. Risks and rollout

  • Data impact: none. There is no migration and existing rows are untouched. A Development database used for the 006 QA may already contain the injected rows from that demonstration; QA must start from a fresh database.
  • Backward compatibility: all breaks are listed in section 5. The API is pre-release and its only consumer, the UI, changes in the same PR. The external feed must send dutyStartDate, expect 201, and stop relying on cross-person duplicate blocking.
  • Date offsets (verified by probe; corrected in Amendment 1): System.Text.Json converts a value with an explicit numeric offset, including +00:00, to server local time. In the UTC container, 2024-01-01T23:30:00-05:00 becomes 2024-01-02. Under Asia/Tokyo, 2024-01-01T23:30:00+00:00 also becomes 2024-01-02. A value ending in Z is not converted and keeps its written date in every time zone tested (UTC, America/Chicago, Asia/Tokyo). This is unchanged from before the task. The contract tells clients to send YYYY-MM-DD; date-only semantics are in task 009's scope.
