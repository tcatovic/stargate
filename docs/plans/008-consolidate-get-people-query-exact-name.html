Plan 008: One GetPeople query object, remove GET /Person/{name}

Contracts: docs/contracts/008/contract.html (with openapi.yaml, data.md, types.ts, tests.md).

Summary and verdict

Verdict: multi (api + ui). The work spans two platforms, and the two halves need nothing from each other except a fixed agreement: PersonFilters is { name?, rank?, dutyTitle? } and GET /Person/{name} no longer exists. The UI part is small (remove getPerson, GetPersonByNameResult and their tests, and update two doc comments). It still gets its own developer, as in 006 and 007, so both halves can run in parallel against the contract.

What this task does (the task's revised Decisions say task 006 already made the name match exact and removed the LIKE code, and task 007 stopped using GetPersonByName):

  1. Delete GET /Person/{name} and GetPersonByName (request, handler and result), plus their tests and the UI's getPerson and GetPersonByNameResult.
  2. Make GetPeople the single query object. MVC binds it with [FromQuery], the validation and Swagger attributes sit on its properties, and the same instance is sent to MediatR.
  3. Validate GET filters the same way as writes: trim first, then apply the shared name rule ([ValidName]).
  4. Add a changelog entry to the README.

One assumption in the task is wrong, and it needs your decision (Q1). After the removal, GET /Person/{anything} does not return 404. It returns 405 Method Not Allowed with header Allow: PUT and an empty body. The reason is that the path still matches the template of PUT /Person/{personId} (PersonController.cs:72), so endpoint routing reports "path known, method not allowed". I observed this on Kestrel (probe below) for /Person/Ada, /Person/123, /Person/Elena%20Vasquez and /Person/%20, and for HEAD and DELETE. Task 007's removed route returned 404 only because /AstronautDuty/{x} matches no other template.

The plan and contract fix the status at 405. That still meets everything else the task requires of the removed route: no handler runs, no person data, no redirect, no 410, and no deprecation period. A routing 404 is possible only by changing PUT (see Q1), so I recommend 405.

A second finding the task did not anticipate (fixed in the plan). If the query object is bound with a plain [FromQuery] GetPeople query, MVC's prefix fallback creates a filter bypass. When any query key equals the C# parameter name, MVC switches to the query. prefix. So /Person?query=x&name=Elena%20Vasquez returned all six people, and /Person?query=x&name=%25 returned 200 with everyone instead of 400, because validation was skipped. It also made ?query.name= a working alias. Pinning the prefix with [FromQuery(Name = "")] on the action parameter removes all three effects. I verified this in the probe, and tests Q5a-Q5e lock it in.

Approach

1. The query object is GetPeople itself (one class)

// Business/Queries/GetPeople.cs
public class GetPeople : IRequest<GetPeopleResult>
{
    [FromQuery(Name = "name"), ValidName, Description("Case-insensitive exact match on the person's full name. Empty or whitespace-only means no filter.")]
    public string? Name { get; init; }

    [FromQuery(Name = "rank"), ValidName, Description("Case-insensitive exact match on the current rank (e.g. MAJ). Excludes people with no assignment.")]
    public string? Rank { get; init; }

    [FromQuery(Name = "dutyTitle"), ValidName, Description("Case-insensitive exact match on the current duty title (e.g. Commander, RETIRED). Excludes people with no assignment.")]
    public string? DutyTitle { get; init; }
}

// Controllers/PersonController.cs
public async Task<IActionResult> GetPeople([FromQuery(Name = "")] GetPeople query, CancellationToken cancellationToken)
{
    var result = await _mediator.Send(query, cancellationToken);
    return this.GetResponse(result);
}
  • Same validation for rank and dutyTitle. Today all three filters use the same pair of attributes (:33, :35, :37), so all three get the same [ValidName]. There is no separate rank or title vocabulary (task 009 territory).
  • Wire names stay exactly name, rank, dutyTitle, set by [FromQuery(Name = ...)] on each property. Without it, Swagger and the 400 errors keys would become Name/Rank/DutyTitle. Binding still ignores case on the key (verified).
  • The prefix is pinned to empty by [FromQuery(Name = "")] on the action parameter (see the warning card). Also needed because [ApiController] would otherwise infer [FromBody] for a complex type. Swagger still lists exactly three parameters (verified on the probe action).
  • init setters bind correctly (verified). No required members, no [JsonIgnore] needed (the request is never serialised). Rank as a property name causes no problem.
  • Coupling. A Microsoft.AspNetCore.Mvc attribute now sits on a Business-layer type. This is accepted: it is what "one class" means, the project is a single assembly, and Business already references StargateAPI.Controllers.BaseResponse. The handler's own Normalize (GetPeople.cs:60) stays as defence in depth for direct MediatR callers and tests.

2. GET trimming is unified with the writes

[ValidName] validates Normalize(value) (an ASCII trim), exactly as POST/PUT do. MVC still binds an empty or whitespace-only value to null (ConvertEmptyStringToNull uses IsNullOrWhiteSpace, which includes NBSP). null means "no filter" and [ValidName] accepts it. Exact list of response changes (from the probe; nothing that returned 200 before returns 400 now):

Input (any of name, rank, dutyTitle)BeforeAfter
Leading or trailing tab, LF, VT, FF or CR around a valid value (%09Elena%20Vasquez, Elena%20Vasquez%0A)400 NameRule200, matches the trimmed value
Raw length over 100 but at most 100 after trimming (%20 + 100 letters)400 "The field name must be a string with a maximum length of 100."200
Over 100 characters after trimming400, message "The field x must be a string with a maximum length of 100." (plus the NameRule message if a character is also invalid)400, exactly one message: the NameRule message (which says "at most 100 characters")
Inner tab, NBSP at an edge, non-ASCII, %, _, punctuation only, injection strings400 NameRule400 NameRule (unchanged)
Empty, spaces only, tab only, NBSP only, parameter absent200, no filter200, no filter (unchanged)

The 400 body shape is unchanged: ValidationProblemDetails with type, title, status, errors and traceId; keys name/rank/dutyTitle; the value is never echoed. These are relaxations, so not breaking for clients, but the changelog records them.

3. Swagger keeps maxLength and pattern

Swashbuckle cannot read [ValidName]. A small ValidNameParameterFilter : IParameterFilter (new file api/Swagger/ValidNameParameterFilter.cs, registered in Program.cs:25 as AddSwaggerGen(o => o.ParameterFilter<ValidNameParameterFilter>())) sets maxLength = InputRules.MaxLength and pattern = InputRules.AllowedCharactersPattern on any parameter whose property or parameter carries [ValidName]. The probe version compiled under Swashbuckle 10.3 / Microsoft.OpenApi 2.x, with the signature Apply(IOpenApiParameter, ParameterFilterContext) and a cast of parameter.Schema to OpenApiSchema. Effects: /Person parameters as before minus minLength: 0; /AstronautDuty GET name gains maxLength/pattern. Request-body schemas are unchanged.

4. Removal

Delete GetPersonByName.cs and the action at PersonController.cs:51-70. Update the endpoint description at :24-28 to say values are trimmed of ASCII whitespace and then validated with the shared name rule. Reword the two comments that mention GetPersonByName, so that grep -rw GetPersonByName exercise1/api exercise1/api.Tests exercise1/ui/src returns nothing. The build fails if anything still references the type.

Alternatives rejected

  • Keep [StringLength] + [RegularExpression] on the properties (Swagger byte-identical, no filter). Rejected because those attributes validate the raw value, so GET would keep disagreeing with the writes, which the task explicitly asks to fix.
  • A separate PersonQuery DTO wrapped into GetPeople. Rejected because the attributes sit fine on GetPeople, and the Decision says split only if they cannot.
  • Route constraint {personId:int} on PUT to get a 404 for GET /Person/Ada. Rejected as the default (Q1): GET /Person/123 would still be 405, and PUT /Person/abc would change from 400 (binding error, task 002) to 404. That is a behaviour change to an endpoint outside this task's scope.
  • A catch-all GET /Person/{*rest} returning 404. Rejected because it keeps code for a route that should not exist, and a handler would run.

Risks and rollout

  • Data: none. Read-only endpoint, no migration.
  • Backward compatibility: callers of GET /Person/{name} get 405 (not 404). They must switch to ?name= and treat an empty people list as "not found". The only in-repo caller (UI getPerson) is removed in the same commit. GET filters accept more input than before (edge control whitespace, padding). No input that was accepted is now rejected.
  • Binding pitfalls: the prefix bypass (mitigated with Name = "" and locked by Q5). Swagger depends on a custom filter (locked by Q9).
  • Rollback: revert the merge commit. No state to undo.
  • Changelog (api/README.md, under "Changelog (breaking changes)", newest first):
    • Task 008 (BREAKING): GET /Person/{name} is removed. Any GET on /Person/{x} now returns 405 Method Not Allowed with Allow: PUT and an empty body (the path is PUT /Person/{personId}'s). Use GET /Person?name=<name>. An unknown person is 200 with an empty people list, not 404. ?name= has been exact since task 006 (C2).
    • Task 008 (not breaking): GET /Person filters are trimmed of ASCII whitespace before validation, like POST/PUT. A leading or trailing tab, LF, VT, FF or CR, or padding beyond 100 characters, now returns 200 instead of 400. An over-long value's 400 message is now the shared name-rule message (one message instead of "The field x must be a string with a maximum length of 100."). Swagger: /Person query parameters no longer show minLength: 0; GET /AstronautDuty's name now shows maxLength and pattern.
  • Not editable by agents: CLAUDE.md's layout line still lists GetPersonByName under Business/Queries/. Please update it yourself (Q3).
