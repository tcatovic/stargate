Observations (not failures)

  1. Retracted: an earlier version of this report claimed the plan's seed expectations were wrong (Kenji assigned CPT/Pilot). That was my error; see Correction below. On a fresh seed the plan is right.
  2. Repeated parameters: the first value wins. ?name=ra&name=Mira -> Mira, Priya (matched "ra"); ?name=a&name=b -> all 6 (matched "a"). No error.
  3. Non-ASCII: the validation pattern accepts any Unicode letter or mark (200, not 400), but case folding is ASCII only, as decided. With person "Élena Ström" (POST, id 8): ?name=Élena matches; ?name=élena, é LENA variants and str%C3%96m do not; STR%C3%B6M matches (ASCII letters fold, ö exact); /Person/élena ström -> 404, exact-case Élena Ström -> 200. Pinned as accepted in Decisions.
  4. GET /Person/ (trailing slash, empty name) is routed to the list and returns 200 with everyone; /Person/%20 is 400.
  5. Over HTTP the 404 body for unknown names is the same JSON shape as a 200 (person:null), and 400 uses ValidationProblemDetails; both match the contract as observed.
  6. The list has no ORDER BY; order observed was by id.
