Observations (not failures)

  1. KNOWN OPEN, demonstrated (case 10, scratch DB h2): POST /Person accepts a' OR Id IS 3 OR 'a (201, id 7) because apostrophes are allowed. Then POST /AstronautDuty {"name":"a' OR Id IS 3 OR 'a","rank":"CPT","dutyTitle":"Injected Role","dutyStartDate":"2026-03-01T00:00:00Z"} returned 200 {"id":10,...} and wrote to a different person: Tomas Lindqvist (PersonId 3). Dump diff: AstronautDetail row 1 (PersonId 3) CurrentDutyTitle Pilot to Injected Role; AstronautDuty row 1 (Tomas, Pilot) got DutyEndDate 2026-02-28 (injected start 2026-03-01 minus one day); new AstronautDuty row 10 (PersonId 3, CPT, Injected Role, 2026-03-01). The injected person (id 7) got no rows. A legitimate Aoife O'Brien Jr. on POST /AstronautDuty got 500 with a body beginning Microsoft.Data.Sqlite.SqliteException ... SQLite Error 1: 'near "Brien": syntax error' plus a stack trace (the duties controller returns exception text; pre-existing). A plain-name duty (Plain Person) worked (200, detail + duty rows for PersonId 9). On BASE, POST /Person already accepted this same string (200, row 9), so the issue is pre-existing; this task keeps apostrophes valid as designed, so the exposure on the duty endpoint is unchanged in kind, and legitimate apostrophe names (now creatable with a documented rule) cannot receive duties.
  2. Expected 409 races log at fail: level with a full stack trace ("UNIQUE constraint failed: Person.Name") from EF (Database.Command and Update loggers) and an Information "Create person rejected: name in use" for pre-check hits. No name values in those logs (parameters shown as ?). Noisy but not a leak.
  3. In Development, a 413 returns a text/plain body with the Kestrel BadHttpRequestException text and stack (~3.8 KB); in Production it is empty (Content-Length: 0). The submitted name is not in it. Contract says the 413 body is unspecified.
  4. Swagger vs contract: CreatePersonRequest has additionalProperties: false while the server ignores unknown properties (observed 201); the 201 response documents no Location header; response content types listed include text/plain and text/json although the server returns application/json; CreatePersonResult has no required list. Documentation only.
  5. Interior whitespace is not collapsed: Mixed Case Double Space is stored with two spaces, and Ada Lovelace is a different name from Ada Lovelace (no 409). Follows the stated rule (only edges trimmed), but is a possible duplicate-lookalike path.
  6. GET /Person/.. returns 404 with an empty body (dot-segment handled by the host before the controller); ?name=.. is 400.
  7. POST-vs-PUT race: in 3 rounds the POST always won, so the "PUT wins, POST gets 409" ordering was not seen. Both orderings are covered by the unique index; no 500 occurred.
  8. The pre-existing VBCSCompiler build server process (started before this QA, pid 233692) is still running; it was not started by this run.
