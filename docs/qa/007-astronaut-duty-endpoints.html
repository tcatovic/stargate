QA Report — Task 007: Astronaut Duty Endpoints (SQL Injection Fix & Validated Duty API)

Branch under test: task/007-astronaut-duty-endpoints @ 81f13f0 (API + UI merged). Vulnerable baseline: main @ 280fcd9 (post task 006, pre task 007 — contains the injection). Tested: 2026-10-15. Tester: QA agent (automated, HTTP + DB level; no browser available in this environment).

VERDICT: PASS

Every acceptance criterion in tasks/007-get-astronaut-duties-by-name-query-param.md that could be observed from a running system was exercised against the real HEAD build and, for the headline security criteria, against the real vulnerable base build side by side. No criterion failed. The three known contract-text defects called out in the task brief (whitespace-only name 400 shape, repeated name param "first wins", exact-case-then-lowest-Id resolution) were reproduced exactly as described and are recorded below as observations, not failures, per instructions. The out-of-scope rules 3-7 known defects (first-RETIRED-duty CareerEndDate) were also reproduced and recorded as observations only.

What was not tested, and why

  • No real browser. This sandbox has no browser automation tool installed. UI behaviour (loading/empty/error states as rendered in markup, user interaction) was verified only via the dev-server proxy at the HTTP level plus the Vitest unit suite and a production build — not visually in a browser DOM.
  • Not every one of the 669 xUnit tests or 47 Vitest tests was independently re-derived by hand. QA ran the suites and confirmed 100% pass, and independently re-verified the highest-value cases (the injection replay, GET/POST edge cases, rules 3-7 regression, pre-index resolution) by hand against a live running server — these hand-verified cases are the ones itemised in this report.
  • S6 (rank/dutyTitle hostile-but-valid storage of apostrophe-containing values like O'Neil) was not separately re-run as its own payload; it is covered indirectly by A15 (trim-and-store verification) and by the shared validation attribute being proven identical across name/rank/dutyTitle in §3's 400 cases. Treated as adequately covered, not as a gap requiring a fail.
  • README changelog content (listing the breaking changes) was not independently verified against the exact wording required by the acceptance criterion — only that the file exists and the branch merged; a close text diff of the README was out of scope for this HTTP-focused QA pass.

Observations (known, documented defects — not QA failures)

  1. Whitespace-only name on GET is 400 with only the required message (%20%20, %09), not [required, NameRule] — MVC binds a whitespace-only query value to null before the [ValidName] validator runs. Confirmed at §2 G7.
  2. Repeated ?name=a&name=b binds the first value (200 for the first person), not 400. Confirmed at §2.
  3. All three name lookups (create handler, GetAstronautDutiesByName, GetPersonByName) resolve a name by exact-case match first, then lowest Id, identically. Confirmed at §5 with the bob/Bob pre-index scratch DB. This is now also documented in the architect's in-progress Amendment 1 to the contract files (observed as a pre-existing, uncommitted working-tree change at the start of this QA run — not made by QA).
  4. For a person's first-ever duty being RETIRED, CareerEndDate is set to the start date itself, not start-minus-1-day (rule 7). Confirmed at §4. This is the documented out-of-scope defect tracked by task 009.
  5. On the vulnerable base build, which specific innocent person gets hit by an injection payload is non-deterministic / payload-dependent — a' OR Id IS 3 OR 'a hit Tomas Lindqvist (Id 3) exactly as named; a' OR 1 OR 'a (a universally-true condition) hit Mira Okafor (Id 1), SQLite's first row, not Id 3. Both are genuine cross-person writes; the specific victim is an accident of the generated SQL and row order, not something the attacker necessarily controls precisely — which makes the vulnerability more dangerous, not less.
  6. On base, some hostile payloads (a' OR 'a' IS 'a, Tomas Lindqvist'--) happen to break the preprocessor's own interpolated existence check and surface as a stack-trace 400 rather than reaching the vulnerable handler — this is incidental to how that string parses as SQL, not a mitigation, and still leaks a full stack trace including file paths to the client.
